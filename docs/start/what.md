2025 年 2 月，Andrej Karpathy 在 X 上发了一段话，大意是：有一种新的写代码方式，我叫它 **vibe coding**——你完全沉浸在感觉里，拥抱指数增长，忘记代码的存在。你看到东西，说出想法，运行，复制粘贴，大部分时候它能跑。

这段话火了。然后被误读了一整年。

他自己在同一条推下面就说清楚了：这适合**周末玩具项目**。到了年底，业内开始把两件事分开讲：

::: card-grid cols="2"

<Card title="Vibe Coding（玩具版）" icon="carbon:play-filled">

- 目标是**做出来**
- 不看代码，不写测试
- 跑通了开心，跑不通就再许愿一次
- 一次性项目、演示、玩

这就是 Karpathy 原本说的那种。没问题，它很好玩。

</Card>

<Card title="Vibe Engineering（工程版）" icon="carbon:tools">

- 目标是**能交付**
- AI 写，人负责：需求、计划、审阅、测试、验收
- 每次改动要能解释为什么
- 会被人用的东西

Simon Willison 后来提了个对照词，就叫 vibe engineering。这门课教的是这个。

</Card>

:::

## 一句话概括你在做的事

**用自然语言写软件。** 你给的不是代码，是意图；AI 给的不是成品，是草稿。

所以你的活儿变成三件：

| 能力 | 具体是什么 | 练法 |
| --- | --- | --- |
| **表达** | 把"我想要"翻译成"谁用、输入什么、输出什么、什么不做、什么算做完" | 写需求卡，见 [想清楚](/loop/think/) |
| **验收** | 看到结果的那一刻知道对不对，而不是"看起来还行" | 每写一条需求，配一条可验证的标准 |
| **纠偏** | AI 跑偏的时候，用最小的改动把它拉回来，而不是推倒重来 | 一次一条任务，一次一个 commit |

这三件事，前两件和编程语言没关系，第三件需要你**读得懂结构**。

## 为什么这门课的主线是需求分析

因为 AI 已经把"打字"这件事解决得差不多了。

你现在可以让 AI 在三十秒里生成八百行代码。它可能全对，也可能有三个隐蔽的错误。区别不在于它有多强，而在于**你有没有办法知道它对不对**。而"知道对不对"的前提，是你先定义过什么叫"对"。

所以这份指南的顺序是反的：

```text
不是：学语法 → 学框架 → 做项目 → 顺便想想需求
而是：想清楚要什么 → 定义什么算做完 → 让 AI 造 → 验证 → 交付
```

后一种顺序里，你依然会学到语法和框架，只不过是在需要的时候学，学的是"我这段代码在干什么"，而不是"这个语言有哪些特性"。

::: tip 一个判断标准
如果你能在不看代码的情况下说清楚：这个程序接受什么、做了什么、什么情况下会出错——那你就是在 vibe engineering。

如果你只能说"它能跑"，那你手里是个黑箱。黑箱可以演示，不能维护。
:::

## 你现在大概是什么水平

大一下，你大概率是这样：

- 写过 C 或 Java 的控制台作业，知道循环、数组、函数是什么
- 见过 HTML，可能照着教程改过颜色
- 没做过"有界面、有人用、会出错"的东西
- 听说过 ChatGPT / Claude / Cursor，但没让它们写过完整项目
- 时间碎片化，一个项目最多给你一个周末

这份指南就是按这个起点写的。不需要你提前会 JavaScript，不需要你会命令行，不需要你有 GitHub 账号——第 0 章会带你装。

## 三条底线

这三条不商量。破一条，你做的所有事都会白费。

::: warning 一、看不懂的东西不交付
不是说你要读懂每一行，是说你要能说出**每个文件的职责**。你说不出来的部分，就是你下次改不动、也修不好的部分。
:::

::: warning 二、没有验收标准的需求不开工
"做个好看的"不是需求。开工前先写下三条能当场试出来的标准，否则你会陷入无限改版的循环。
:::

::: warning 三、代码挂你的名字，责任就是你的
AI 生成的代码出问题，锅不在 AI。交上去的作业、发给同学用的工具、传到 GitHub 上的仓库，署的是你的名。
:::
