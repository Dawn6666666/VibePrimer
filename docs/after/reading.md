不列书单，列**值得花一小时的东西**。每一条都写清"读完你该多会什么"。

按顺序看，别跳。

## 一 · 先把词的来历搞清

**Andrej Karpathy 2025 年 2 月的那条推文**
搜 `karpathy vibe coding` 就能找到原文。

- 他造这个词时的原意：不看代码、全部接受、凭感觉推
- 他自己补了一句：适合周末玩具项目
- 你会多会：知道这个词原本是**自嘲**，不是方法论

如果你只读一样东西，读这个。读完之后你会明白，为什么这本指南花了两章讲验收。

**Simon Willison 关于 vibe engineering 的那篇**
他的博客 `simonwillison.net`，搜 `vibe engineering`。

- 同一件事的工程版本：一样用 AI 生成，但规格、测试、审查一样不少
- 那句「解释不了就不提交」，是他说的
- 你会多会：一个能直接用在作业和实习里的判断标准

## 二 · 官方的最佳实践

**Anthropic 的 Claude Code 最佳实践文档**
官网文档里搜 `Claude Code best practices`。

值得看的四处：

1. **采访式提示** —— 让它反过来问你。你在 [想清楚](/loop/think/) 用的就是这招
2. **证据式验收** —— 要截图、要命令输出，不要"已完成"
3. **CLAUDE.md** —— 项目约定写一次，省几十次重复交代
4. **纠错两次就 `/clear`** —— 同一个问题修两次没好，换会话重开

第 4 条看着反直觉。它的理由是：错的上下文会一直影响后面的判断，你越解释它越歪。

**GitHub Spec Kit / Kiro 的文档**

- 两者都在推同一件事：spec → plan → tasks → implement
- 你会多会：知道「先写规格再写代码」不是这本指南发明的，是行业正在收敛的做法

## 三 · 数据与证据

**Chroma 2025 年的 context rot 研究**
搜 `context rot chroma research`。

- 18 个模型，输入越长，表现越差，无一例外
- 有篇论文叫 *Lost in the Middle*：关键信息在长输入中间时，模型最容易漏
- 你会多会：为什么长任务要分段，为什么要 `/clear`，为什么别把两千行文件硬塞给它

**关于 AI 编造包名的论文**（arXiv 2406.10279）

- 57.6 万个样本，约 19.7% 建议的包并不存在
- 这类攻击有了名字：slopsquatting —— 有人专门注册这些不存在的包名，等你装
- 你会多会：`npm install` 报 404 时，第一反应是"它编的"，而不是"我打错了"

::: warning 一个具体做法
装任何 AI 推荐的包之前，先去 npm 官网搜一下。

存在、有下载量、最近还在更新——三条都满足再装。三条里缺一条，就是它编的。
:::

## 四 · 中文的

**vibe-hub 之类的聚合站**（搜 `vibe coding 中文`）

- 教程质量参差，但**案例多**
- 看法：只看"他做了什么、卡在哪"，跳过所有"十分钟精通"

**B 站上的实战录屏**

- 挑那种**不剪加速的**，看他卡住的时候怎么处理
- 你会多会：知道别人的 workflow 里也有大量试错，不是一次成功

## 怎么读

一条规矩：**一小时只读一篇，带着一个问题读。**

比如读 Karpathy 那条推文时，带的问题可以是："他说的这种玩法，用在课程表上会死在哪一步？"

读完能答出来，这一小时就值了。读十篇答不出来，那十小时白花。

## 别读的东西

| 类型 | 为什么 |
|---|---|
| 「7 天精通 AI 编程」 | 7 天能学会的是复制粘贴 |
| 「100 个神级提示词」 | 提示词的效力来自上下文，清单里的词换个项目就废 |
| 「AI 将取代程序员」 | 和你今天要交的作业无关 |
| 只讲工具的评测 | 工具三个月换一轮，评测写完就过期 |

第三类特别费时间。**你不需要对行业下判断，你需要把手上这个东西做完。**

## 最后一份阅读材料

你自己的 `BUGS.md`。

两周之后回去看，你会发现里面一半的坑你已经不会再踩了——不是记住了，是**手熟了**。

那才是你真的学会了。
