完成两个案例后，可以继续做个人工具、参与别人的项目，或和同学做一个有真实用户的小产品。三条路线会练习不同能力，不必按固定顺序。

## 给自己做工具

先记录自己反复遇到的小问题，再挑一个能用较小范围验证的想法。

```markdown
- 课表截图在相册里难翻，想按周查看
- 学习记录总要手动分类，想减少输入
- 读书笔记格式不统一，想保存一个可复用模板
- 收藏的文章很多，想做一个本地待读清单
```

洗衣机是否空闲这类实时问题还需要真实数据来源，单靠网页无法知道设备状态。选题时先问“数据从哪里来”。

| 个人本地版想法 | 主要练习 |
| --- | --- |
| 课表、倒计时、番茄钟 | 数据与渲染 |
| 记账、打卡、学习记录 | 表单、localStorage、筛选 |
| 单词卡、复习提醒 | 数组、日期和状态 |
| 个人物品借用记录 | 表单、列表和时间 |

这里的“个人本地版”只保存当前浏览器的数据。它不能让多位同学共同编辑同一份记录，也不需要一开始就引入后端。

## 参与别人的项目

这条路线会练习阅读已有代码、遵守项目约定和接受反馈。

在 GitHub 搜索 `good first issue`，先读项目的 README、贡献指南和 issue 讨论，确认问题仍然存在，并了解维护者希望怎样处理。项目是否活跃不能只看最近一次提交，也要看 issue 和 PR 的回应。

第一次可以选择一项有明确依据的小改动：补充文档中的缺失步骤、为已确认的问题添加测试，或修复一个能够复现的输入校验。不要把“数字改常量”当成必然受欢迎的贡献，也不要未经讨论添加新功能。

提交 PR 时说明动机、复现方式、改动范围和验证结果。维护者可能很忙，也可能不回复；被拒绝或没有回应都不等于你的练习没有价值。

## 和同学做有人使用的项目

真实用户能帮助你发现需求遗漏，但多人共享也会带来新的技术边界。

| 想法 | 个人演示版 | 多人真实使用还需要 |
| --- | --- | --- |
| 活动报名 | 本地表单和确认提示 | 服务端存储、隐私告知、数据管理和防滥用 |
| 课程资料索引 | 本地链接列表 | 分享权限、版权确认、内容维护 |
| 考试倒计时 | 本地日期和展示 | 通常仍可保持静态，不必强行加后端 |
| 公共物品借用 | 单机记录 | 共享数据库、身份与权限、冲突处理 |

收集报名信息前，只收集必要字段，说明用途和保留时间，并取得同意。不要上传无权分享的课程资料。多人版在上线前重新阅读 [安全](/craft/safety/)。

## 一个两周练习安排

| 时间 | 产出 |
| --- | --- |
| 第 1–2 天 | 问题清单，选一个数据来源明确的小问题 |
| 第 3 天 | 需求卡和验收标准 |
| 第 4 天 | 文件职责、任务清单和风险 |
| 第 5–8 天 | 分步实现，每天保留一个可运行提交 |
| 第 9–10 天 | 根据风险补边界测试并修复 |
| 第 11 天 | README 和交付包 |
| 第 12 天 | 请一位目标使用者独立操作，记录卡点 |
| 第 13–14 天 | 选择一条反馈修改并复测 |

观察用户时先别急着教。对方点错的位置，可能说明按钮命名、信息顺序或说明文案需要调整。

## 什么时候评估框架

出现组件重复、复杂交互状态、页面路由或团队协作成本时，可以评估框架。重复三次列表渲染也可以先用函数解决，多页共享状态也不是框架的唯一理由，`app.js` 超过某个行数更不是通用阈值。

学习框架前，先能读懂当前 JavaScript 的数据流和状态转换。引入框架应当解决已经说清楚的问题，而不是只因为它看起来更专业。

下一次练习仍然可以使用同一套方法：明确需求，拆小任务，检查改动，独立验证，记录限制。项目变大后，再逐步补自动化测试、后端、权限和团队协作流程。
