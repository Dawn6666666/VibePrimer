番茄钟那次，方案的重点是"砍掉多少"。

这次的重点是**顺序**——四个文件、四件事，先做哪个，决定了你什么时候能看见结果。

## 第一条提示词

```text
需求在 REQUIREMENT.md 里，数据结构和验收标准都在。

现在不要写代码，先给我两部分：

一、数据结构的最终形态
把十门课写成 JS 数组，我看一眼字段对不对。

二、实现步骤
每步写清三件事：
1. 改哪个文件
2. 这一步跑完，我在页面上能看到什么变化
3. 怎么验证这一步做对了

要求：
- 一共不超过 6 步
- 每步的代码改动不超过 40 行
- 先渲染后交互，先静态后状态
- 主动告诉我哪一步最容易返工，以及为什么
```

最后一句是这次的关键。番茄钟那次你问的是「主动排除什么」，这次问的是「哪一步最容易返工」——因为四个文件的项目，返工不是重写，是**改一处、三处跟着动**。

## 它返回的方案

```md
## 一、数据结构

const COURSES = [
  { name: '高等数学 A(2)', teacher: '王', room: 'B203', day: 1, start: 1, span: 2, weeks: 'all' },
  …十门课
];

字段说明：
- day: 1–5（周一到周五）
- start: 1–6（第几节开始）
- span: 1–6（连上几节，默认 1）
- weeks: 'all' | 'odd' | 'even'

## 二、实现步骤

1. 建四个文件，data.js 放十门课
   改动：index.html / style.css / data.js / app.js
   能看到：一个空表格，表头周一至周五，左侧 1–6
   验证：双击 index.html，表头出现，控制台无报错

2. app.js 里写 buildColumns + render，把所有课画上去（不合并）
   改动：app.js
   能看到：每门课出现在一个格子里
   验证：数一下，十门课一门不少

3. 加 rowspan 合并
   改动：app.js（buildColumns 里加 'skip'，render 里跳过 skip）
   能看到：连上两节的课占两行
   验证：周一第 1 节高数占两行，第 2 节没有独立空格

4. 加单双周过滤 + 周次按钮 + localStorage
   改动：app.js / index.html
   能看到：点按钮，周三第 1 节在线性代数和大学物理之间切换
   验证：切到第 2 周 → 刷新 → 还是第 2 周

5. 加冲突检测 + 标红 + 提示行
   改动：app.js
   能看到：周四第 5 节标红，右上角一行提示
   验证：把两门课改成不同时间，提示消失

6. 手机宽度适配
   改动：style.css
   能看到：窗口拖窄，表格横向滚动
   验证：375px 宽度下页面不左右晃

## 三、最容易返工的一步

第 3 步。合并单元格要动 buildColumns 的返回结构，
而 render 已经在用这个结构了。如果第 2 步把渲染写死在循环里，
第 3 步就得把整段渲染代码重写一遍。

建议：第 2 步就按 buildColumns 的结构写，即使那时还没有合并。
```

::: tip 这段回答值多少
最后一段——「第 3 步最容易返工，建议第 2 步就按最终结构写」——这就是你花钱买的东西。

它没有替你写一行代码，但它让你少重写一遍 `render`。

**方案的价值不在步骤列表，在对"哪里会疼"的判断。**
:::

## 你砍掉的三件事

对着验收标准看，有三样东西方案里没提，但你和 Agent 聊天时都冒出过：

| 冒出来的想法 | 砍掉的理由 |
|---|---|
| 点格子弹一个详情窗，显示课程号和学分 | 验收标准里没有"查看详情"。而且课程号你自己都不记 |
| 导出成图片，方便发群里 | 手机截图比这快。做了要先引一个 canvas 库，项目从四个文件变成五个 |
| 拖动格子调课表 | 一个拖拽库 + 一次数据迁移 + 一堆边界情况。它够再开一个项目 |

第三条特别值得记：**「听起来很酷」和「这版需要」是两回事**。判断标准只有一条——验收标准里有没有它。

## 你补上的两件事

反过来，有一件事方案里没写，但你得补上：

| 补的 | 为什么 |
|---|---|
| 数据越界时跳过而不是崩 | 你手写数据，一定会写错一次。第 1 条的验收标准是"打开就能看"，不是"打开就白屏" |
| 单双周判断收成一个函数 | 不然第三节那个 bug 你要改三处 |

第一条现在看着像多此一举。等到 Bug 1 找上你的时候，你会庆幸。

## 怎么样算一个能开工的计划

三条：

1. **每一步都能在页面上看见** ——「重构一下数据层」不算一步，你看不见它。  
2. **每一步都能一句话验收** ——「十门课一门不少」能验，「渲染正确」不能。  
3. **每一步做完，整个项目还能跑** —— 合并做到一半发现表错位了，你应该能 `git restore` 回到上一步，而不是被卡在半路。

第 3 条是四个文件项目的命门。番茄钟只有一个文件，你随手改坏了还能全选重来。四个文件不行——**你必须随时有一个能跑的版本**。

## 一句话模板

```text
需求在 REQUIREMENT.md 里。

先不要写代码。给我：
1. 数据结构的最终形态（字段 + 取值范围）
2. 不超过 6 步的实现顺序，每步写清：改哪个文件、页面上能看到什么变化、怎么验证
3. 哪一步最容易返工，为什么，以及前面哪一步要提前按它的样子写

每步代码改动不超过 40 行。
```

最后那句「哪一步最容易返工」可以套在任何多文件的活上。新手方案与老手方案的区别，就在这一句。
