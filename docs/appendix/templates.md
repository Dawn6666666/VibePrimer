按当前任务选择模板，不必十二份全部使用。占位内容要替换成项目事实，模板本身不能代替需求判断和实际验证。

## 1. 需求访谈

适合项目刚开始、关键决定还没想清楚时。

```text
我要做【项目】，给【谁】在【场景】使用，运行方式是【双击 / 本地服务 / 部署】。
先不要写代码。最多问我 10 个会影响实现的问题，一次列完，按重要性排序。
不要讨论配色和字体。回答后，把最终决定整理到 REQUIREMENT.md。
```

需要逐项深入讨论时，可以改成“一次问一个问题”。两种方式最终都要保存决定，不把被否决的方案写进需求。

## 2. 需求卡

```markdown
# 【项目名】需求卡

## 使用者与场景
【谁，在什么时间和设备上使用，现在怎样解决】

## 输入
【用户操作、数据来自哪里、哪些值可以为空】

## 输出与功能规则
【界面、文件、保存行为、异常和边界规则】

## 约束
【运行方式、依赖、网络、隐私、交付条件】

## 本版不做
【明确排除的功能；按实际项目填写，不凑数量】
```

一个填好的片段：

```markdown
## 输出与功能规则
- 初始显示 25:00，开始、暂停、继续和重置共用明确状态。
- 自然归零后今日数加 1；重置不计数。
- 刷新后倒计时回到 25:00，今日数保留。
```

## 3. 验收标准

```markdown
| # | 操作 | 预期结果 |
| --- | --- | --- |
| 1 | 【具体操作和测试数据】 | 【可观察、可判定的结果】 |
| 2 | 【另一项独立操作】 | 【结果和允许误差】 |
```

写不出操作和结果的需求，通常还需要改写。长时间行为可以提供明确的测试配置，验完恢复正式配置。

## 4. 要方案

```text
读取 REQUIREMENT.md。先不要写或修改代码。
给出文件职责、实施顺序、每步的可见结果和验收操作。
指出主要风险、最容易返工的一步，以及每条验收由哪一步覆盖。
等我确认后再执行。
```

步骤数量按项目决定。不要用统一的行数上限代替职责划分。

## 5. 分步指令

```text
执行 TODO.md 第【N】条：【目标】。
预计修改【文件】；如果必须改其他文件，先说明原因。
遵守【实现约束】，处理【边界情况】。
不要增加无关功能或依赖。

完成后列出：实际改动、运行的命令和结果、手动验收、未验证项。
```

实现和测试、HTML 和脚本有时需要一起修改，不必机械限制“一次只能一个文件”。范围应围绕一个内聚目标。

## 6. Bug 报告

```text
先不要改代码。
操作：【步骤、输入、环境】
期望：【结果】
实际：【现象】
频率：【每次 / 偶发及已知条件】
报错：【原文和位置，没有就写无】
最近改动：【相关 commit 或代码】

请区分已确认事实和待验证假设。每个可能原因给一步最小验证操作。
```

## 7. 对照代码和需求审查

```text
只读，不修改。对照 REQUIREMENT.md 和当前 diff：
1. 哪条需求没有实现或实现不一致？
2. 哪个改动超出了当前任务？
3. 哪些边界没有测试？
引用相关文件和代码，并说明影响。行号和解释仍由我在编辑器中核对。
```

要求引用代码能帮助定位，但不能保证模型一定读过或理解正确，仍需人工检查。

## 8. `TODO.md`

```markdown
# 【项目名】TODO

需求与验收见 REQUIREMENT.md。需求变化时同步更新，不另写一套不同标准。

## 当前里程碑
- [ ] 【可独立运行和验收的任务】
- [ ] 【下一项任务】
- [ ] 边界测试与交付说明

## 当前阻塞与风险
【已确认的问题、需要的决定、最容易返工的位置】
```

任务过多时按里程碑分组或缩小本版范围。不要为了不增加条数，把多个不相关目标塞进一项。

## 9. README

```markdown
# 【项目名】

【它是什么，给谁用】

## 运行
【环境要求、安装、命令、入口和成功标志】

## 使用
【核心操作和预期结果】

## 数据与已知限制
【保存位置、隐私、未支持功能、当前测试范围】

## 实现与验证
【技术栈、文件职责、关键设计、实际运行的测试】

## AI 使用说明
【按事实填写 AI 和本人分别完成的工作，并遵守课程要求】
```

没有发现问题时可以写“在当前测试范围内暂未发现其他问题”，不要编造“已知问题”。

## 10. 项目规则文件

适合支持 `AGENTS.md`、`CLAUDE.md` 或其他规则约定的工具。加载方式以工具文档为准。

```markdown
# 项目约定

## 运行与验证
【准确命令、入口、测试和手动验收】

## 文件职责
【只写 Agent 不容易从代码迅速发现的信息】

## 当前约束
- 修改前读取 REQUIREMENT.md
- 不读取 .env 或真实凭据
- 不顺手增加无关功能或重构
- 页面无意外横向溢出；宽表格仅在指定容器内滚动
```

规则文件提供指导，不等于权限强制执行。绝对不能发生的操作还要配置权限、沙箱或其他确定性限制。

## 11. 交付前自查

```markdown
- [ ] 每条需求都有对应的实际操作和通过结果
- [ ] 重复点击、空输入、超长输入和特殊字符符合预期
- [ ] 刷新后，应保留和应重置的数据都符合需求
- [ ] 窄屏无意外溢出，宽表格只在指定容器滚动
- [ ] 断网时有可用结果或明确提示，不会无限等待
- [ ] 换浏览器检查核心行为，记录未覆盖的差异
- [ ] 临时日志和废代码已处理，有用途的日志和注释保留
- [ ] 当前源码和 Git 历史没有真实 key，被跟踪的 .env 已处理
- [ ] README 与实际版本一致
- [ ] 部署后从公开链接复测；不部署则标记不适用
- [ ] 截图按交付需要准备，内容来自当前版本
```

## 12. 复盘与 `BUGS.md`

```markdown
## 项目复盘
| 阶段 | 用时 | 卡点 | 下次怎样提前发现 |
| --- | --- | --- | --- |
| 想清楚 | | | |
| 定计划 | | | |
| 生成并运行 | | | |
| 调试 | | | |
| 交付 | | |

## 一条 BUGS.md 记录
- 现象与复现：【操作、期望、实际、频率】
- 根因：【验证后确认的原因】
- 修复：【改动范围】
- 复测：【通过的操作和未覆盖项】
- 预防：【新增测试或下次开工时的动作】
```

复盘结论尽量写成可执行动作，例如“生成前先核对需求文件中的刷新规则”，不要只写“以后认真一点”。
