能直接复制走的东西。每条都标了「什么时候用」，别全都用——**模板多了本身就是负担**。

## 1. 需求访谈

什么时候用：任何项目的第一句话。

```text
我要做【一句话说清做什么】，【运行方式：双击打开 / 跑起来看 / 部署上去】。

先不要写代码。用提问的方式帮我把需求问清楚：
最多问我 10 个问题，一次问完，按重要性排序。
只问会改变实现方式的问题，不要问配色、字体、动效。
```

## 2. 需求卡

什么时候用：访谈结束，写进 `REQUIREMENT.md`。

```md
# 【项目名】

## 谁用
【谁 + 什么场景 + 现在怎么解决的】

## 什么时候用
【具体时刻】

## 输入
【用户给什么 / 数据从哪来】

## 输出
【屏幕上出现什么】

## 约束
- 【运行方式】
- 【用什么技术，不用什么技术】
- 【性能/体积/兼容性的硬要求】

## 不做什么
- 【一条一条列】
```

「不做什么」至少写三条。**这是最省你时间的一节。**

## 3. 验收标准

什么时候用：需求卡写完，开工之前。

```md
## 验收标准

| # | 标准 | 怎么验 |
|---|---|---|
| 1 | 【可观察的结果】 | 【一句话操作】 |
| 2 | … | … |
| 3 | … | … |
```

写不出「怎么验」的那条，说明它不是验收标准，是愿望。删掉或者改写。

## 4. 要方案

什么时候用：需求定了，还没写第一行代码。

```text
需求在 REQUIREMENT.md 里。

先不要写代码。给我：
1. 涉及哪些文件，每个文件负责什么
2. 不超过 6 步的实现顺序，每步写清：改哪个文件、跑完能看到什么、怎么验证
3. 哪一步最容易返工，为什么，前面哪一步要提前按它的样子写

每步代码改动不超过 40 行。
```

## 5. 分步指令

什么时候用：每一次让它改代码。**这是你用得最多的模板。**

```text
【要做什么，一句话】

要求：
1. 只改【文件名】，别的文件别动
2. 【具体实现约束，比如"合并逻辑先算成数组，不要在渲染里直接算"】
3. 【边界情况怎么处理】
4. 不要引入依赖，不要改【不能动的东西】

改完告诉我：改了哪几行、为什么这么改。
```

第 1 条和第 4 条是护栏。**每当它"顺手"改了别的东西，回来看这两条是不是漏了。**

## 6. Bug 报告

什么时候用：任何一次"不对"。

```text
报告一个 bug：
1. 我做了什么：【具体操作】
2. 我期待什么：【具体结果】
3. 实际发生什么：【具体现象】
4. 报错原文：【完整复制，包括文件名和行号】

先不要改代码。告诉我可能的原因，按可能性排序，以及怎么验证每一个。
```

## 7. 让它自己查

什么时候用：bug 报了两次还没修好，或者交付前。

```text
不要改代码。读一遍【文件名】，用一句话回答：
1. 这个文件里哪个函数最可能出问题，为什么
2. 我想实现【X】，现在的代码里哪一行和这个意图不一致
用证据说话：引用行号和那一行的代码。
```

「用证据说话：引用行号和代码」这句，能把它的回答从猜变成查。

## 8. TODO.md

什么时候用：方案审完，开工之前。

```md
# 【项目名】 TODO

## 需求摘要
【三行以内】

## 验收标准
1. …（和 REQUIREMENT.md 一致）

## 任务
- [ ] 1. 【能看见结果的一步】
- [ ] 2. …
- [ ] 3. …
- [ ] 4. 边界测试
- [ ] 5. README + 部署

## 已知风险
- 【方案里说的那个最容易返工的地方】
```

任务写 5–8 条。超过 10 条说明你还没拆完，先拆项目，别拆任务。

## 9. README

什么时候用：交付前，二十分钟。

```md
# 【项目名】

一句话：它是什么，给谁用。

## 怎么用
1. 【第一步】
2. 【第二步】

## 特性
- 【用户能感知到的东西，不要写技术栈】

## 已知问题
- 【诚实地写，写清楚边界】

## 实现说明
- 【技术栈 / 文件结构 / 一个关键设计决定】

## 致谢
由【工具名】辅助生成，需求分析、结构设计与测试由本人完成。
```

「已知问题」这一节不要留空。写「无」的项目，通常是没测。

## 10. CLAUDE.md / AGENTS.md

什么时候用：同一个人（你）反复给同一个项目下同类指令时。放在项目根目录，Agent 每次启动会读。

```md
# 项目约定

## 这是什么
【一段话】

## 技术栈
原生 HTML/CSS/JS。不用框架，不用构建工具，不引入依赖。

## 文件分工
- index.html：结构
- style.css：样式
- data.js：数据，只放数据
- app.js：逻辑

## 规则
- 改代码前先读 REQUIREMENT.md
- 一次只改一个文件
- 新增字段必须同步更新 data.js 里所有记录
- 不要动 .env、不要动 .git

## 验收
- 双击 index.html 能跑
- 手机宽度下横向滚动
```

写一次，省后面几十次的重复交代。**这是这个领域投入产出比最高的一件事。**

## 11. 交付前自查

贴进项目根目录的 `CHECK.md`，或者就放在桌面。

```md
## 交付前

- [ ] 验收标准逐条手上过一遍
- [ ] 连点主要按钮五次
- [ ] 空输入 / 超长输入 / 特殊字符
- [ ] 刷新页面，该留的留该清的清
- [ ] 手机宽度
- [ ] 换一个浏览器
- [ ] 断网
- [ ] 搜索 console.log / TODO / 注释掉的代码
- [ ] key 不在代码里，.env 在 .gitignore 里
- [ ] README 五节齐全
- [ ] 部署后打开线上链接看一次
- [ ] 三张截图：首屏 / 核心操作 / 结果
```

十二条，最后六条是最常被跳过的。

## 12. 复盘

什么时候用：项目交了之后，趁还记得。

```md
## 复盘

| 阶段 | 花了多久 | 卡在哪 |
|---|---|---|
| 想清楚 | | |
| 定计划 | | |
| 生成并运行 | | |
| 发现问题并修改 | | |
| 检查并交付 | | |

最大的一次返工是什么？起因是哪一步没做够？
下次开工前，我要多做的一件事是：
```

最后一行必须写成一个**动作**。「想清楚一点」不是动作，「开工前先让它问我 10 个问题」是。
