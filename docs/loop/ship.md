自己熟悉操作路径，不代表别人也能顺利使用。交付前要重新检查功能、运行条件和已知限制，让接收者不必靠猜来启动项目。

## 三层检查

### 按验收标准实际操作

打开 `REQUIREMENT.md`，逐条执行，不要只凭记忆打勾。

- “点开始后数字每秒减 1”：用秒表对照一段时间。
- “刷新后数据不丢”：分别测试刷新和重新打开浏览器。
- “空输入有提示”：真的提交一次空输入，记录实际提示。

如果修改过相关代码，即使这条标准上次通过，也要重新测试。

### 检查边界情况

<Gate group="ship" />

边界测试没有固定通用清单。输入为空、重复点击、刷新、存储不可用、窗口变窄等情况，应按项目实际风险选择。

### 检查交付物

| 检查 | 目的 |
| --- | --- |
| 不引用自己电脑上的绝对路径 | 避免换电脑后找不到资源 |
| 源码和 Git 历史中没有真实密钥 | 避免分享后泄露 |
| 不提交 `node_modules` 等可再生成目录 | 减小仓库体积 |
| README 包含运行、使用和限制 | 让别人可以独立操作 |
| 截图能反映真实版本 | 方便快速了解项目 |
| AI 使用说明符合课程要求 | 如实交代分工 |

## 一次番茄钟边界测试

```text
1. 打开页面，等待 10 秒，应保持 25:00。
2. 开始后再连续点击主按钮，按钮应按开始、暂停、继续切换，计时速度不变。
3. 暂停后等待 5 秒，数字不变；继续后从原位置走。
4. 运行中刷新，按本案例需求回到 25:00，今日完成数不变。
5. 测试时长暂时改为 3 秒，归零后停止，标题改变，今日数只增加 1。
6. 归零后再次开始，应从完整测试时长重新计时。
7. 运行中和暂停后分别重置，应回到初始值且不增加今日数。
8. 完成一次后刷新和重新打开，今日数保留；随后恢复 TOTAL = 25 * 60。
9. 用开发者工具设备栏把视口设为 375px，按钮不重叠，页面无意外横向滚动。
```

如果修改系统时间，基于 `Date.now()` 的倒计时也可能跳变。时间戳差值主要解决后台回调被节流的问题，不能抵抗系统时钟被手动修改。首版可以把系统时钟跳变列为已知限制，不必把它当作必须通过的项目。

## 交付包里放什么

```text
pomodoro/
├── index.html
├── REQUIREMENT.md
├── TODO.md
├── README.md
├── screenshots/
│   ├── 01-首页.png
│   └── 02-计时中.png
└── BUGS.md             ← 有调试记录时保留
```

部署到网上后，可以在 README 顶部写访问链接。本地交付则写清入口文件和需要的软件。

## README 示例

```markdown
# 番茄钟

一个本地单页番茄钟，无外部依赖。页面本身不请求外部 API。

## 运行
双击 index.html。

## 使用
1. 点击「开始」启动 25 分钟倒计时。
2. 点击「暂停」暂停，再点「继续」接着计时。
3. 点击「重置」回到 25:00，不计入完成数。
4. 自然归零后，今日完成数加 1，并保存在当前浏览器中。

## 当前限制
- 刷新或重新打开后，本次计时进度不保存，回到 25:00。
- 今日完成数只保存在当前浏览器；清除网站数据后会丢失。
- 不支持自定义时长、休息倒计时和声音提醒。

## 实现与验证
- HTML / CSS / JavaScript，单文件，无框架。
- 使用 Date.now() 与目标结束时间计算剩余时间。
- 已测试开始、暂停、继续、重置、自然归零、刷新和手机窄屏。

## AI 使用说明
按实际情况填写 AI 参与了哪些代码或文档工作，本人完成了哪些需求、审查和测试。
```

AI 使用说明是交代贡献的一种方式，具体格式要遵守教师、课程或比赛规定。不要照抄“需求与测试由本人完成”，除非确实如此。

## 部署：按项目需要选择

| 方式 | 适合 |
| --- | --- |
| 文件夹或压缩包 | 课程作业、本地工具 |
| GitHub Pages | 纯静态 HTML / CSS / JavaScript |
| Vercel / Netlify | 需要构建或持续部署的前端项目 |

GitHub Pages 首次发布可以这样做：

1. 在 GitHub 新建一个空仓库，不要重复添加本地已有的 README。
2. 如果本地还没有远程仓库，配置地址并首次推送：

   ```bash
   git branch -M main
   git remote add origin https://github.com/你的用户名/仓库名.git
   git push -u origin main
   ```

   已配置 `origin` 时不要重复添加，先用 `git remote -v` 检查。
3. 打开仓库 `Settings → Pages`，在 Build and deployment 中选择 **Deploy from a branch**。
4. 选择 `main` 分支和 `/ (root)`，保存并等待部署。仓库根目录需要有 `index.html`。
5. 打开 Pages 给出的地址，再测一次核心功能。

页面白屏时先看 Console 和 Network。纯静态文件可以检查 `./style.css` 等相对路径和文件名大小写；Vite 等构建项目通常要配置 `base`，不能盲目替换所有 `/` 开头的内容。

部署意味着文件会被上传到托管平台。课程、姓名、教室等数据应先匿名化，不要把“本地版不上传”写成部署版也成立的承诺。

## 用新会话检查 README

```text
你只能阅读我接下来提供的 README，不要参考项目历史或其他文件。
按这份说明操作，指出缺少的运行条件、命令、入口和预期结果。
不要修改代码。
```

当前 Agent 已经知道项目细节，容易替 README 补全没说出的信息。使用新会话并只提供 README，更接近新读者；有条件时，再请一位同学实际照做。

## 最后的收尾顺序

1. 按验收标准和边界清单测试。
2. 补齐 README、AI 使用说明和截图。
3. 删除临时调试日志与注释掉的废代码；有明确用途的日志可以保留。
4. 清理后重新启动，再跑一次核心验收。
5. 查看 diff，提交交付版。
6. 打包或发布，并从交付地址再验证一次。
