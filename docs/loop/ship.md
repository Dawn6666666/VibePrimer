「能跑」和「能交」之间，隔着一整个下午。

这不是夸张。你自己跑，用的是你最熟的那条路径：你记得要先点哪个按钮，知道哪个输入会炸，知道刷新一下就好。换成别人——或者两周后的你——这些默契全都不存在。

**交付的意思是：别人不需要问你，就能把它跑起来、用起来、并且知道它哪里还不完美。**

## 三层检查

### 第一层：对着验收标准逐条过

打开你的需求卡，一条一条试。**不是在脑子里过，是手上过一遍。**

- 「点开始后数字每秒减 1」→ 真的点一次，数五秒
- 「刷新后数据不丢」→ 真的刷新
- 「空输入有提示」→ 真的提交一个空的

这一步最常见的失败是"我记得它是好的"。记忆不可靠，尤其是你昨天改过八次。

### 第三层：交付本身

代码能跑，和你把东西交出去，是两件事。

| 检查 | 为什么 |
| --- | --- |
| 路径里没有 `C:\Users\你\Desktop` | 换台电脑就 404 |
| 没有硬编码的 API key | 传上 GitHub 就等于公开 |
| 没有 `node_modules` 进仓库 | 几十 MB，别人 `npm install` 就能有 |
| README 里写了怎么跑 | 别人不看代码也能启动 |
| 有截图 | 老师在打开之前就知道你做完了 |
| 写了「已知问题」 | 显得你清醒，而且避免别人踩 |

## 一次完整的边界测试

以番茄钟为例，我会这么试。你也这么试：

```text
1. 打开页面 → 什么都不点，等 10 秒 → 应该还是 25:00
2. 点开始 → 连点五次开始 → 应该只有一个计时器在跑，速度不变
3. 点开始 → 点暂停 → 等 5 秒 → 数字不应该动
4. 点开始 → 刷新页面 → 状态应该是你设计的那种（继续/暂停/归零），且你解释得清
5. 把系统时间调快 → 计时是否还在走（用时间戳差值的实现会正常）
6. 缩小窗口到手机宽度 → 按钮不重叠、不超出屏幕
7. 完成一个番茄 → 今日统计 +1 → 刷新 → 还是 +1
8. 连点「重置」十次 → 不应该报错，也不应该变负数
```

八条试完，你会抓到至少一个。抓到了别烦，这就是这一步存在的意义。

## 交付包里放什么

```text
我的番茄钟/
├── index.html          ← 代码
├── style.css
├── script.js
├── README.md           ← 怎么跑、怎么用、已知问题
├── screenshots/
│   ├── 01-首页.png
│   └── 02-计时中.png
└── BUGS.md             ← 可选：你踩过的坑
```

如果部署到了网上，README 顶部加一行链接。这比任何描述都有说服力。

## README 模板

五节，二十分钟能写完。别写多。

```markdown
# 番茄钟

一个本地单页番茄钟，双击 index.html 就能用。没有依赖，不联网。

## 怎么跑
双击 index.html。
（需要本地服务的项目写：`npm install` 然后 `npm run dev`，打开 http://localhost:5173）

## 怎么用
1. 点「开始」，倒计时 25 分钟
2. 点「暂停」暂停，再点「继续」接着走
3. 点「重置」回到 25:00
4. 完成一个番茄，下方「今日」数字 +1，数据存在浏览器里

## 已知问题
- 切到别的标签页时，倒计时会滞后 1–2 秒（浏览器的定时器节流，用时间戳差值已缓解）
- 不支持自定义时长
- 没有声音提醒，只在归零时改页面标题

## 用了什么
- 纯 HTML / CSS / JavaScript，无框架无依赖
- 计时逻辑用 `Date.now()` 差值，不用累加
- 数据存 `localStorage`
- 由 Claude Code 辅助生成，需求、拆分、验收、修 bug 由本人完成
```

最后一行不是形式主义。**说清哪里用了 AI，是让"你做了什么"变得可信的唯一方式。** 交作业时尤其如此：老师反感的从来不是用 AI，是明明用了却说全手写。

## 部署：选一个

| 方式 | 适合 | 大概多久 |
| --- | --- | --- |
| 直接把文件夹发给对方 | 课程作业、老师要收 | 1 分钟 |
| GitHub Pages | 静态页面，想有个链接 | 15 分钟 |
| Vercel / Netlify | 有构建步骤（Vite/Next）的前端 | 20 分钟 |

静态页面部署到 GitHub Pages 的最短路径：

1. 建一个 GitHub 仓库，把代码推上去
2. 仓库 Settings → Pages → Source 选 `main` 分支 `/root`
3. 等一分钟，访问 `https://你的用户名.github.io/仓库名/`

如果页面白屏，九成是路径问题：把 `index.html` 里所有 `/xxx` 开头的路径改成相对路径 `./xxx`。

## 演示：三张截图

别人不会读你的代码，他们会看你的图。三张就够：

1. **首屏**——最能说明"这是什么东西"
2. **核心操作中**——说明它真的在动
3. **一个边界情况**——比如空输入的提示，或完成后的状态

截图前把浏览器书签栏关掉（`Ctrl+Shift+B`），窗口拉正。这不用教，但很少有人做。

## 让 AI 帮你查漏

最后一招，很有效：

```text
假设你是一个从没见过这个项目的人，只读 README。
按 README 的步骤，你能顺利跑起来吗？哪里会卡住？

列出 README 里缺的信息，按重要性排序。不要改代码。
```

它会告诉你"没写 Node 版本要求"、"没说端口被占用怎么办"、"没说这个按钮是干嘛的"——全是你自己想不到的地方。

## 交付的最后一小时

1. 按验收标准过一遍（手上过）
2. 按边界清单过一遍
3. 写 README
4. 截图
5. 删掉所有 `console.log` 和注释掉的废代码
6. 最后提交一次，commit message 写「交付版」
7. 压缩打包，或把链接发出去

第 5 条别省。留着一堆 `console.log` 和注释掉的代码，看起来像"还在施工"。两分钟能清干净。
