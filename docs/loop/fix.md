这一步是整份指南里最耗时间的，也是唯一没法被 AI 替代的。

生成代码这件事，AI 几秒钟就做完了。判断"哪里不对、为什么不对、改成什么"——这件事只能你来。因为**只有你知道你想要的到底是什么**。

## 卡住的原因，八成不是你技术不行

是信息不够。你发过去的是一句"还是不行"，AI 收到的是零信息，它只能猜。猜一次不对，你再发"还是不行"，它又猜。

三回合之后，你们都乱了。

区别不在礼貌，在**可验证的线索**：期望、实际、报错、最近改了什么、你的猜测。

## 固定四步

不管什么 bug，都按这四步走。跳过任何一步，你都会多花一倍时间。

### 一、复现：让它每次都错

写下三个短句：

```text
操作：打开页面 → 点开始 → 等 2 秒 → 点暂停 → 再点开始
期望：从暂停的位置继续倒数
实际：从头 25:00 开始
频率：每次都这样
```

**能稳定复现的 bug 才是能被修的 bug。** 如果一个 bug 时有时无，先别修它——先让它稳定出现（固定输入的顺序、清缓存、换一个浏览器试试）。

### 二、读报错：只看第一行和你的文件

浏览器里按 `F12` → Console。终端报错往上翻到最开头。

```text
Uncaught TypeError: Cannot read properties of null (reading 'textContent')
    at renderTimer (script.js:42:18)
    at script.js:51:3
```

怎么读：

1. **第一行**是错误类型和消息：`Cannot read properties of null` —— 你在一个 `null` 上调用了 `.textContent`
2. **往下找第一处提到你自己文件的行**：`script.js:42` —— 问题就在那一行附近
3. 剩下的 `at ...` 是调用链，第一版可以不管

人话翻译：第 42 行你取一个元素，但它不存在（多半是 `querySelector` 的 id 拼错了，或者脚本在元素出现之前就执行了）。

::: warning 别跳过"读"
让 AI 读报错是快的，但**你自己读三次之后，就会开始认识它们**。`null`、`undefined`、`404`、`is not a function`——这些词出现几次你就记住意思了。

完全依赖 AI 读报错的人，三个月后还在问"报错了改一下"。
:::

### 三、缩小范围：二分查找

不知道哪儿错了，就砍一半。

- **注释掉一半代码**，错还在 → 问题在另一半
- **回滚到上一个能跑的 commit**，然后只恢复一部分改动 → 找出是哪一处引入的
- **换一个输入**：换个数据、关掉一个功能、换浏览器。差别在哪，问题就在哪

这招很笨，但它保证你三十步之内一定找到，而不是靠灵感。

### 四、一次一个假设

不要一口气改三个地方，然后发现"好了"。你不知道是哪个改动治好的，下次也治不好。

```text
假设：定时器没有在暂停时被 clearInterval，所以还在后台跑。
验证：在 clearInterval 那一行加一句 console.log('cleared')。
结果：日志没打印，说明 clearInterval 根本没执行。
```

一次一个假设，一次一个验证。慢就是快。

## 让它先诊断，别急着改

最有用的一个指令：

```text
先不要改代码。
根据我给的信息，列出三个最可能的原因，按可能性排序。
每个原因告诉我：怎么用一步操作验证它。
```

为什么这样更好：

- 你拿到了三个假设，而不是一次瞎改
- 你能自己验证，验证完你对这个项目的理解就深了一层
- 就算它猜错，你也排除了三个方向

反过来，你说"帮我修一下"，它会直接改。改对了你也不知道为什么，改错了你得重新描述一遍。

## 三次法则

**同一个 bug，修了三次还没好，停下来，回滚。**

不是第四次会好，是你们俩已经陷在同一个错误假设里了。这时候继续打补丁，代码会越来越乱，你会得到一个新的、更难的 bug。

回滚步骤：

```bash
git log --oneline        # 找到最后一个"能跑"的 commit
git restore .            # 丢掉所有未提交改动
# 如果已经提交过坏代码：
git reset --hard <那个 commit 的哈希>
```

然后重新描述需求，告诉 AI：**"我们换个思路"**，并附上你那三次失败尝试的结论。它在新上下文里通常能给出完全不同的方案。

## 常见报错速查

| 看到这个 | 大概是 | 先做什么 |
| --- | --- | --- |
| `Cannot read properties of undefined/null` | 取一个不存在的东西 | 检查变量名、`querySelector` 的 id、数组是否为空 |
| `xxx is not a function` | 你调的东西不是函数（拼错了，或作用域不对） | 打印一下它的类型 |
| `404 Not Found` | 文件路径错了 | 检查大小写、相对路径、有没有多余的前缀 |
| `Blocked by CORS policy` | 浏览器拒绝了跨域请求 | 本地开发用相对路径；或让后端加响应头 |
| `NaN` | 数字运算里混进了非数字 | 打印参与运算的每个值 |
| `Unexpected token '<'` | 拿到的是 HTML 而不是 JS/JSON | 路径错误，或者接口返回了错误页 |
| 页面一片空白，控制台没报错 | 元素没渲染，或 JS 提前 return | 加 `console.log` 从入口往下打 |
| 改了代码但页面没变 | 缓存 / 没保存 / 打开了错误的文件 | 硬刷新 `Ctrl+Shift+R`，确认文件路径 |

## 修好之后，写一行日志

别修完就翻页。在项目的 `BUGS.md` 里加一行：

```markdown
- 暂停后计时还在跑 → setInterval 没清，且用一个全局 id 覆盖了上一个
- 刷新后数据没了 → 存的是对象，localStorage 只能存字符串，忘了 JSON.stringify
```

一周之后，这张表会变成你自己的错误模式清单。你会发现自己的 bug 有一半是重复的——这比任何教程都值钱。

## 心态

::: tip bug 是信息，不是失败
报错不是"我不行"，是"这里有一个我不知道的事实"。

一个学期下来，写了多少行代码不重要。**你修好了多少个自己也解释不清的问题**，才决定你到了哪个层次。
:::
