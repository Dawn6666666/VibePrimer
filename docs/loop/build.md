生成阶段循环执行以下五个动作：

::: steps

1. **发出指令**：限定具体任务项与文件范围，严禁越界发散。
2. **看 Diff**：检查改动范围，核对是否有无关修改或未经同意新增的外部依赖。
3. **本地运行**：双击网页或启动开发服务，在真实环境中运行预览。
4. **对照验收**：对照需求卡与实施计划中的验证动作逐项核对。
5. **打卡提交**：验收通过后立即执行一次原子 Git 提交，锁死阶段进度。

:::

每一轮只处理一条小任务。这样出错时，你知道问题最可能来自哪次改动，也能在确认结果后及时保存版本。

## 发出指令：限定范围

不要只说“把番茄钟做好”，可以写：

```text title="单任务派发提示词"
做 TODO.md 里的第 2 条：开始、暂停、继续和重置。
只修改 index.html 中与计时和按钮有关的代码。
不要增加其他功能。
完成后说明修改位置、验证方法和未验证的部分。
```

任务目标和验收标准来自需求文件，文件限制用于控制影响范围。若确实需要修改其他文件，让 Agent 先说明原因。

## 看 diff：先知道它改了什么

Agent 说“改好了”后，先打开 VS Code 的源代码管理面板（`Ctrl+Shift+G`），逐个查看文件。

| 看什么 | 需要追问的情况 |
| --- | --- |
| 修改范围 | 出现了与任务无关的文件或函数 |
| 行为变化 | 新增代码改变了已有按钮、数据或页面结构 |
| 依赖和资源 | 出现需求未允许的 `import`、安装命令或外部链接 |
| 验收对应关系 | 看不出哪段代码实现当前任务 |

新增行数可以帮助你安排审查时间，但不能单独证明质量。首次页面骨架可能有几十行，小改动也可能引入严重问题。你要能解释主要改动为什么存在。

## 运行：先确认项目类型

| 项目形态 | 怎么运行 | 注意事项 |
| --- | --- | --- |
| 单个 HTML 文件 | 双击，或用 Live Server 打开 | 修改后刷新；普通 CSS 和传统脚本可以使用相对路径 |
| 有 `package.json` | 先看 `scripts`，再按说明安装依赖并运行对应脚本 | 常见命令是 `npm install` 和 `npm run dev`，以项目实际脚本为准 |
| Python 命令行程序 | 在项目目录运行 `python main.py` | macOS / Linux 常使用 `python3`，Windows 也可能使用 `py` |

开发服务器启动后，终端通常会显示 `http://localhost:端口`。打开这个地址，运行期间不要关闭对应终端。

运行前检查当前目录是否为项目根目录。`pwd` 可以显示路径，Windows CMD 可直接运行 `cd`。如果提示端口占用，可以按项目工具支持的方式换端口，或关闭占用程序。

## 先排查环境和路径

下面的报错有不同来源，不能一概归因于代码或环境。

| 报错里出现 | 可能原因 | 先试这个 |
| --- | --- | --- |
| `command not found` / `不是内部或外部命令` | 工具未安装或 PATH 未生效 | 检查安装，重开终端 |
| `EADDRINUSE` | 端口被占用 | 换端口或关闭占用程序 |
| `Cannot find module` | 依赖未安装，也可能是导入名称或路径错误 | 确认依赖已安装，再核对 import 和文件名 |
| `EACCES` / 权限不足 | 当前用户无权访问某个路径，或程序写入了不合适的位置 | 查看完整路径和权限，不要直接用 `sudo` 掩盖问题 |
| `Unexpected token '<'` | 请求 JS / JSON 时收到了 HTML 错误页 | 打开 Network 查看请求地址、状态码和实际响应 |

中文或空格路径在少数旧工具里可能有兼容问题，但不是所有报错的答案。保留完整报错，逐个验证假设。

## 页面能运行，但代码看不懂

先用三分钟找三个位置：

1. **入口**：HTML 里的 `<script>`，或 `package.json` 的 `main` / `scripts`。
2. **数据**：保存当前状态的变量，例如 `state`、`data`、`list`、`current`。
3. **显示更新**：搜索 `textContent`、`innerHTML`、`render`、`update`。

然后让 Agent 概括结构：

```text
用 10 行以内解释这个文件：有哪些状态，什么时候变化，变化后哪里更新页面。
再列出入用户点击按钮到页面更新的调用链。不要逐行复述代码。
```

注释也有用途。外部约束、非显而易见的原因和边界条件值得写；“定义一个变量”“让 i 加 1”这类复述代码的注释可以删掉。阅读方法详见 [读懂代码](/craft/read/)。

## 一次生成太多，怎样重来

先看 `git status`，区分已跟踪文件的修改和新建文件：

```bash
git status
git diff
git restore .
```

`git restore .` 只会恢复已跟踪文件的工作区改动，不会删除未跟踪的新文件，也不会默认清除已暂存改动。不要把它当成通用的“回到上次提交”。

新文件如果确认不需要，先根据 `git status` 的清单核对并备份，再手动删除。已有改动可能有用时，先做 WIP 提交或复制备份。

之后缩小指令：

```text
这次只做静态页面：一个 25:00 的数字和两个按钮。
不要 JavaScript，不添加其他区域。完成后停止，等我验收。
```

如果只改一个目标仍然频繁影响无关代码，先检查指令是否明确、函数是否承担过多职责，再决定是否需要拆文件。不要盲目拆分。

## 什么时候提交

确认当前改动通过验收后立即提交，例如：

- 静态页面能打开，`添加番茄钟静态页面`
- 开始和暂停符合需求，`实现开始与暂停`
- 修复后通过复测，`修复暂停后仍计时`

提交前查看 diff 和暂存内容。提交只记录当时加入的内容，之后的新修改仍需再次提交。
