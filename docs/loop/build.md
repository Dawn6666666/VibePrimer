这一步最容易变成"看 AI 打字"。别。

你在这一步要做的是四件事的循环，每一圈只做一条任务：

```text
发出指令 → 看 diff → 跑起来 → 看清结果 → 提交
```

一圈大概 10–20 分钟。四个动作里，**最容易被跳过的是"看 diff"和"提交"**，而这两个恰恰是让你不至于失控的东西。

## 发出指令：限定范围

不要这样说：

> 把番茄钟做好

要这样说：

```text
做 TODO.md 里的第 2 条：开始/暂停。
只改 script.js 和 style.css 里跟这个按钮有关的行。
不要动 HTML 结构，不要加别的功能。
做完告诉我改了哪几行。
```

三句限定，挡住三种失控：一次只做一条（范围）、别碰别的文件（隔离）、说清改了什么（可审阅）。

## 看 diff：两分钟，省两小时

它说"改好了"之后，**先别看浏览器，先看 diff**。

VS Code 左边点源代码管理（`Ctrl+Shift+G`），点那个文件，红绿对比。你只看三件事：

| 看什么 | 出现这个就危险 | 怎么办 |
| --- | --- | --- |
| **改到的文件** | 你只让它改 `script.js`，它顺手改了 `index.html` | 当场问："为什么动 index.html？" |
| **新增的行** | 一次多了 80 行，而你只要一个按钮 | 让它拆小，或者回滚重来 |
| **依赖** | 冒出 `import` 或 `npm install` | 需求卡说了不装依赖，直接拒绝 |

::: tip 一个具体习惯
每次看 diff，先拉到最下面看**总行数**：`+12 −3` 这种是健康的，`+180 −96` 就该警觉。

不是不能有 180 行，是你必须能解释这 180 行。解释不了，就是黑箱。
:::

## 跑起来：三种场景

| 项目形态 | 怎么跑 | 注意 |
| --- | --- | --- |
| 单个 HTML 文件 | 双击，或在 VS Code 里右键 → Open with Live Server | 改了要刷新；Live Server 会自动刷新 |
| 有 `package.json` | 终端里 `npm install` 一次，然后 `npm run dev` | 第一次装依赖要等，正常 |
| 有 `main.py` / 命令行程序 | 终端里 `python main.py` | 要在项目文件夹里跑，路径才对 |

跑之前的通用检查：

- 终端的**当前目录**是不是项目根目录（`pwd` 或看提示符）
- 有没有红色报错**上一行**被滚掉了（向上翻）
- 端口是不是被别的程序占着（`3000` 最常撞车）

## 环境级错误怎么办

这类错误和你的代码无关，全是环境问题。出现了先看这张表，别急着让 AI 改代码——它也不知道你的电脑上装了什么。

| 报错里出现 | 意思是 | 先试这个 |
| --- | --- | --- |
| `command not found` / `不是内部或外部命令` | 这个工具没装，或者没进 PATH | 重装并勾选 "Add to PATH"，然后**重开终端** |
| `EADDRINUSE` / `端口已被占用` | 端口被别的程序占了 | 换端口（`--port 3001`），或关掉那个程序 |
| `Cannot find module` | 依赖没装 | 在项目目录里 `npm install` |
| `EACCES` / `权限不足` | 权限问题（多见于 macOS/Linux） | 看错误里提到的路径，别用 `sudo` 硬来 |
| `Unexpected token '<'`（浏览器里） | 你请求的地址返回了一个 HTML 页面，不是 JS | 路径写错了，检查文件名大小写 |

::: warning 一个反复出现的坑
Windows 上路径含中文或空格，会让 `npm`、`python`、部分 Agent 直接失败，而且报错信息看起来毫无关系。

新建项目时就把文件夹放在 `C:\dev\` 或 `D:\code\` 下面，别放桌面上的中文文件夹里。
:::

## 能跑，但你看不懂

这很正常，而且不该跳过。**看不懂的代码，你改不动也修不好。**

三分钟读法，按顺序：

1. **找入口。** 哪个文件是"从这开始跑的"？HTML 里看 `<script>`，Node 项目看 `package.json` 的 `main`/`scripts`。
2. **找数据。** 这个程序把状态存哪儿？变量名里带 `state`、`data`、`list`、`current` 的那些。
3. **找渲染。** 数据怎么变成屏幕上的东西？搜索 `innerHTML`、`textContent`、`render`、`update`。

然后让 Agent 帮你把结构说出来：

```text
用 10 行以内解释这个文件的结构：它有哪些状态，什么时候变化，
变化之后哪里会重新渲染。不要逐行解释。
```

想更直观，就要图：

```text
把这个文件里数据的流动画成一个 mermaid 流程图：
用户点按钮 → 哪个函数 → 哪个状态变了 → 哪里重新渲染。
```

::: tip 一个反直觉的建议
**别让 AI 给你加注释。** 满屏"// 定义变量"的注释会让你以为看懂了，其实什么都没看懂。

更好的问法是："这段代码里，哪三行是最关键的？" 只要三行。看懂那三行，剩下的都是包装。
:::

## 它一次给你太多

如果你发出去一句"做个番茄钟"，收到四个文件、600 行——**不要往下走**。

先回滚：

```bash
git status          # 看它动了什么
git restore .       # 全部丢掉（前提是你上一次提交是干净的）
```

然后重发指令，这次带上范围：

```text
太大了。我们重新来，一次只做一小块。
现在只做一件事：在 index.html 里写一个居中的大数字 25:00，
配一个不能点的「开始」按钮。不要 JS，不要 CSS 文件，样式写在 <style> 里。
```

## 它把你的代码改坏了

会发生。最常见的两种：

1. **它重写了整个文件**，顺手删了你自己加的两行
2. **它"顺手优化"**，改了一个你没让它改的函数

发现方式就是看 diff。处理方式：

```bash
git diff                      # 确认它删了什么
git restore script.js         # 丢掉这个文件的改动
```

然后重新下指令，这次更窄：**"只改 renderTimer 这个函数里的第 3 行到第 8 行，别的地方一个字都不要动。"**

如果它做不到"只改这几行"，说明这个文件已经太长了，该拆。

## 什么时候提交

一句话：**在你确认"这个状态是好的"那一刻，立刻提交。**

- 第一版能打开 → 提交，`能打开的空壳`
- 按钮能点 → 提交，`加开始暂停`
- 抓到并修好一个 bug → 提交，`修：暂停后计时还在走`

别攒。攒三个功能再提交，等于把三个可能出错的东西绑在一起，出错时你分不清是谁的问题。
