需求卡写完，下一句最容易说错的话是：**"开始写吧。"**

说了这句，Agent 会立刻给你一堆文件。它没有错，是你在还没看清路线的时候就让车开了。

定计划这一步，你要拿到两样东西：**文件清单**（这个项目由哪几个文件组成，各自负责什么）和**任务清单**（按什么顺序做，每条怎么验）。然后你要做的事是——砍掉一半。

## 让 Agent 先交方案，别交代码

不同工具里这叫法不一样，本质是同一件事：**禁止它写代码，先让它说。**

::: code-tabs

@tab Claude Code

直接说「先别写，给我方案」，或者按 `Shift+Tab` 切到 Plan Mode——这个模式下它只能读文件和思考，不能改文件。看完方案你点同意，它才开始动手。

@tab Cursor

对话框里选 **Plan** 模式（不是 Agent 模式）。它会先出一份计划让你确认。

@tab 通用提示词

哪个工具都能用，也不需要任何特殊功能：

```text
不要写任何代码。先读我的需求，然后只输出四样东西：
1. 这个项目需要哪几个文件，每个文件一句话说清职责
2. 实现顺序：先做什么，后做什么，为什么
3. 每一步做完之后，我怎么验证它是对的
4. 你觉得哪里可能出问题（浏览器限制、数据格式、性能）
输出完等我确认。
```

:::

最后那个模板建议存进备忘录。它比任何"高级提示词技巧"都有用。

## 一份好的计划长什么样

以番茄钟为例。差的是这样（AI 默认吐出来的）：

> 我将为你创建一个完整的番茄钟应用，包含精美的 UI 设计、响应式布局、深色模式支持、任务列表功能、数据统计图表、声音提醒、桌面通知……代码会分为 HTML、CSS、JavaScript 三个文件……

这不是计划，这是推销。你既不知道它要做几个文件，也不知道先做哪个。

好的是这样：

```text
文件清单（3 个）
- index.html    页面结构：一个大数字、两个按钮、一行今日统计
- style.css     样式：居中布局、按钮状态（可用/禁用）、响应式一条 media query
- script.js     逻辑：计时器状态机（idle/running/paused）、每秒 tick、localStorage 读写

实现顺序
1. 静态骨架：数字写死 25:00，两个按钮不能点      → 验证：打开页面看到样子
2. 开始/暂停：点开始每秒减 1，再点暂停            → 验证：数 5 秒，显示 24:55
3. 归零和重置：到 00:00 停止，重置回 25:00        → 验证：手动把时间改成 3 秒试
4. 刷新保持：把当前状态写进 localStorage          → 验证：刷新页面数字不变
5. 今日统计：完成一个 +1，存本地                  → 验证：完成两次，刷新还在

风险点
- 浏览器对 setTimeout 的节流：切到别的标签页时计时会变慢，需要用时间戳算差值
- 自动播放限制：没用户交互时不能播声音，第一版用改标题代替
- localStorage 里存的是字符串，读出来要 JSON.parse，空值要兜底
```

差别在哪？它**每一步都能单独验证**，而且它主动说出了两个你根本不知道的坑。

## 审计划的五个问题

拿到计划，按顺序问：

| 问题 | 判断标准 | 不对就怎么办 |
| --- | --- | --- |
| 文件是不是太多 | 一个下午的项目，超过 6 个文件就是过度设计 | 让它合并，"合成 3 个文件" |
| 有没有多余的依赖 | 需求里没写要框架，计划里出现了 `npm install` | 直接说"不要任何依赖" |
| 顺序对不对 | 第一步应该是**能看到东西**，不是"搭建架构" | 要求"先给我一个能打开的白板" |
| 风险点写了吗 | 一条都没有 = 它没想过会出什么问题 | 追问"这个方案最可能在哪里失败" |
| 有没有"顺便" | 出现需求卡里没有的功能 | 全部删掉，写进「以后再说」 |

::: warning 最常见的过度设计
你只想做一个单页小工具，它给你：路由、状态管理、组件库、构建工具、TypeScript 配置、ESLint 配置、测试框架。

这些在真实项目里都对。但在你只有一个下午、且还没跑通第一行的时候，它们每一个都是**新增的失败点**。

一句话挡住："这是课程作业级别的小工具，请用最少的文件和最少的依赖实现，不要引入框架和构建工具。"
:::

## 把计划写到磁盘上

计划只在对话框里，会随着上下文变长被挤掉。写到文件里，它就一直在。

让 Agent 建一个 `TODO.md`：

```markdown
# 番茄钟 · 任务清单

## 需求摘要
25 分钟倒计时，本地单文件，不做登录和多语言。

## 验收标准
1. 点开始后数字每秒减 1
2. 归零时标题变成「休息一下」
3. 刷新页面状态不丢

## 任务
- [ ] 1. 静态骨架（写死 25:00）
- [ ] 2. 开始/暂停
- [ ] 3. 归零与重置
- [ ] 4. 刷新保持
- [ ] 5. 今日统计

## 已知风险
- setTimeout 在后台标签页会被节流 → 用时间戳差值
- 自动播放限制 → 第一版只改标题
```

然后每一轮只说一句：**"做第 2 条，做完把勾打上。"**

这个文件有三个好处：你随时知道进度；上下文爆了之后新会话能接着干；一周后你回来看得懂自己做过什么。

## 任务该拆多细

三条标准，全中才算合格：

1. **15 分钟内能验证**——超过这个时间，你对"做完没做完"就没有把握了
2. **一句话说清验收**——"按钮能点"不合格，"点开始后数字每秒减 1"合格
3. **做完之后项目仍然是能跑的**——不能出现"这一步做完先别运行，等下一步一起"

第三条最容易被忽略。有些人习惯"先把三个文件都建好，最后一起跑"，结果第一次运行就撞上五个错误，你还得分辨是哪一个引起的。

## 计划被推翻了怎么办

会发生的。做到第 3 步你发现"刷新保持"需要改数据结构，前面的计时器逻辑得动。

这时候**不要**让 AI 现场打补丁。回到计划：

```text
停一下。第 4 步需要改数据结构，现在这个结构存不下。
先别改代码。告诉我：如果要支持刷新保持，第 2、3 步的实现要改哪里？
给我两个方案，一个改动小的，一个更干净的，各自代价是什么。
```

计划是一份可以修改的文件，不是一份承诺。改它不丢人，绕过它才丢人——绕过它的每一次，都会在两天后变成一个你解释不清的 bug。

## 一句话模板

```text
按上面这份计划做第 N 条。只改这一条需要改的地方，
不要顺手优化别的，不要重构已有代码。
做完告诉我：改了哪些文件、怎么验证、有什么副作用。
```

前半句限定范围，中间半句挡住"顺便"，最后半句让你知道发生了什么。这三句话，你会用一整个学期。
