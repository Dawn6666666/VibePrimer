需求确认后，先让 Agent 给出实现方案。你需要看清项目由哪些文件组成、按什么顺序做、每一步怎样验证，以及哪些需求被遗漏或擅自增加。

## 让 Agent 先交方案

:::: tabs

@tab Claude Code

可以直接说“先别写，给我方案”，也可以按 `Shift+Tab` 切到 Plan Mode。具体权限以当前工具显示为准，看完方案后再决定是否允许修改。

@tab Cursor

如果当前版本提供 Plan 模式，可以先在 Plan 中讨论方案。没有该模式时，使用下面的通用提示词，并检查它是否仍然修改了文件。

@tab 通用提示词

```text title="方案需求提示词"
不要写或修改任何代码。先读 REQUIREMENT.md，只输出：
1. 文件清单，以及每个文件的职责
2. 实施顺序和原因
3. 每一步的验证操作与预期结果
4. 主要风险，例如浏览器限制、数据格式和边界情况
输出后等我确认。
```

## 一份可执行的计划

下面这种回答虽然列了很多内容，却没有对应需求，也没有说明每步怎样验收：

> 我将创建完整的番茄钟应用，包含精美 UI、响应式布局、深色模式、任务列表、统计图表、声音提醒和桌面通知，代码分为 HTML、CSS、JavaScript 三个文件。

它确实提到了三个文件，但没有交代文件职责和实施顺序，还加入了需求之外的功能。可以改成下面这样：

```text
运行文件
- index.html：包含页面结构、样式和脚本，双击即可运行

项目文档
- REQUIREMENT.md：需求与验收标准
- TODO.md：任务、进度和调整后的事项

实施顺序
1. 静态骨架：显示 25:00、操作按钮和今日完成数
   验证：双击页面，内容完整，按钮暂时不响应
2. 开始、暂停、继续和重置
   验证：运行 5 秒约减少 5 秒；暂停 3 秒不变；继续后接着走；重置回到 25:00
3. 归零与今日计数
   验证：测试时长设为 3 秒，归零后停止、标题变化、今日数只增加 1 次
4. 本地保存与边界检查
   验证：刷新后倒计时回到 25:00，今日数保留；重置不增加完成数

主要风险
- 后台标签页可能减少 setInterval 回调次数，剩余时间应根据目标结束时间计算
- localStorage 读出的是字符串，需要转换并校验；存储不可用时计时仍应可用
- 测试短时长后要恢复 TOTAL = 25 * 60
```

这里的“状态”可以只理解为程序当前处于未开始、运行中或已暂停哪一种情况。按钮文字和允许执行的操作都由这个状态决定。

时间戳方案也不复杂：运行时记录目标结束时间 `endAt`，每次页面更新时用 `endAt - Date.now()` 计算剩余毫秒数。这样即使后台标签页少执行了几次回调，回到页面后仍会按真实经过的时间重算。

## 审计划时问五个问题

| 问题 | 需要检查什么 | 怎么修改 |
| --- | --- | --- |
| 文件是否必要 | 每个文件是否有清楚职责 | 合并只为“架构”而存在的文件 |
| 依赖是否必要 | 是否出现需求未要求的框架或安装步骤 | 说明本版的依赖限制 |
| 首步能否看到结果 | 是否先搭了很多暂时无法运行的配置 | 要求先提供可打开的最小页面 |
| 风险是否具体 | 是否只写“注意兼容性”而没有具体问题 | 追问最可能失败的输入或环境 |
| 是否遗漏或增加需求 | 任务和验收能否逐条对应 `REQUIREMENT.md` | 删除额外功能，补齐遗漏项 |

文件数量没有通用的上限。小项目应优先减少不必要文件，大项目则按职责拆分，不能机械地用“六个文件”判断好坏。

## 把计划保存为 `TODO.md`

```markdown
# 番茄钟任务清单

需求与验收标准见 REQUIREMENT.md。本文件只记录实施顺序和进度；需求变化时，两份文件一起更新。

## 任务
- [ ] 1. 静态页面：25:00、操作按钮、今日完成数
- [ ] 2. 开始、暂停、继续和重置
- [ ] 3. 归零、标题提示和今日计数
- [ ] 4. 本地保存、边界复测和恢复正式时长

## 当前约定
- 单个 index.html，无外部依赖
- 刷新后倒计时回到 25:00，今日完成数保留
- 只有自然归零才计为完成，重置不计数
```

每一轮可以说：“做 TODO.md 第 2 条，完成后更新勾选状态。”新会话也能通过需求卡和任务清单恢复进度。

## 任务拆到什么程度

一条任务应当有一句话能说清的验收方法，完成后项目仍然可以运行。如果必须等后面三条任务都完成才能第一次运行，通常说明拆法不合适。

15 分钟可以作为小任务的参考，但不必为了赶时间省略验证。首次搭建骨架可能比后续修改多很多代码，这也是正常现象。

## 计划需要调整时

做到一半发现原方案无法支持需求，先停止生成，说明已确认的事实，再讨论调整：

```text
第 3 步发现当前数据结构无法保存今日日期。
先别改代码。说明需要调整哪些任务和验收标准，给出改动最小的方案，以及它会影响哪些已有功能。
```

计划可以修改，但要记录原因，并同步更新 `REQUIREMENT.md`、`TODO.md` 和验收结果。不要只改对话框里的一句话，让项目文件继续保存旧约定。

## 执行单条任务的模板

```text
按 TODO.md 做第 N 条，只修改这条任务需要的内容。
不要顺手增加功能或重构无关代码。
完成后说明：改了哪些文件、怎样验证、实际验证了什么、还有什么没验证。
```

计划确认后进入 [生成并运行](/loop/build/)。
