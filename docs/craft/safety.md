小项目也会涉及密钥、依赖、隐私和 Agent 权限。下面是最常见的一组风险，不代表检查完就可以保证整个系统安全。

## API key 和凭据

不要把真实 key 写进源码、提示词或截图：

```js
const API_KEY = 'sk-xxxxxxxxxxxxxxxx'
```

Node 项目可以把密钥放在不提交的 `.env`，并提交只有变量名的 `.env.example`：

```text
# .env，不提交
API_KEY=sk-xxxxxxxxxxxx
```

```text
# .env.example，可以提交
API_KEY=
```

`.gitignore` 至少包含 `.env`。在支持 `--env-file` 的 Node 版本里，可以这样加载：

```bash
node --env-file=.env server.js
```

```js
const key = process.env.API_KEY
if (!key) throw new Error('缺少 API_KEY')
```

环境变量不会仅因创建了 `.env` 就自动出现在 `process.env` 中，需要 Node 的加载功能、加载库或部署平台注入。

更重要的一点：原生浏览器 JavaScript 没有安全的 `process.env`。纯前端里的 key 最终都可能被使用者看到，`.env` 和构建工具也不能改变这一点。需要保密的 key 应放在受控后端，由后端调用服务。

如果 key 已经公开，立即吊销并轮换，检查调用记录和费用。删除文件或提交不能替代吊销；之后还要清理 Git 历史和公开副本，减少继续传播。

## 不核实就安装依赖

模型可能写错包名，也可能推荐已经废弃或不适合的包。安装前核对官方文档、包名、版本、发布者和仓库，确认项目确实需要它。

404 可能来自拼写、版本、私有包、registry 配置或包被移除，不能直接断定是模型编造。下载量低或很久没更新也不等于包不存在；下载量高和最近更新同样不能证明安全。不存在和不可信是两个问题。

初学案例可以尽量少用依赖，但不必把“任何依赖都不装”当成长期规则。需要安装时，先知道它解决什么问题，以及不用它能否更简单。

## 隐私和工具输出

使用云端模型时，你粘贴的文字、上传的代码附件和 Agent 读取的工具输出都可能发送到服务商。本地模型的数据路径不同，应查看具体产品说明。

不要提供真实身份证号、学号、手机号、账号密码、私人地址和同学的个人记录。演示时使用虚构数据。课程表、宿舍和固定行程组合起来也可能暴露个人作息，公开部署前要匿名化。

## Agent 权限

在项目目录启动可以减少默认操作范围，但项目目录不是权限沙箱。进程通常仍能访问当前操作系统用户有权限访问的其他位置，具体取决于工具配置。

| 风险操作 | 更稳妥的做法 |
| --- | --- |
| 用管理员或 `sudo` 权限运行 Agent | 使用普通低权限账号 |
| 自动批准所有命令 | 查看命令和路径，逐个批准高风险操作 |
| 执行来源不明的 `curl ... \| bash` | 阅读脚本和官方安装说明，不盲目执行 |
| 读取陌生文件同时开放网络与密钥 | 把内容当作不可信数据，限制读取、网络和凭据权限 |
| 需要更强隔离时仍只依赖当前目录 | 使用容器、独立低权限用户或专用环境 |

网页、文件和图片里的文字可能包含提示词注入，例如要求 Agent 忽略规则并发送密钥。不要把它们当成可信指令，尤其不要在读取不可信内容时同时开放敏感工具。

## 上线前的最低排查

这几项只是起点：

1. 认证使用成熟方案，不在前端写死账号密码，不自行发明密码存储方式。需要密码时采用合适的密码哈希和服务端会话。
2. 服务端按用户和资源检查权限。公开只读接口可以合理存在，简单口令或 IP 白名单不能替代完整的认证与授权。
3. 不可信文本用 `textContent` 显示，不直接拼进 `innerHTML`；SQL 使用参数化查询，不拼接用户输入。
4. 数据库、管理后台和调试端口不直接暴露到公网，部署前检查平台访问控制。

纯前端登录页和 `localStorage.loggedIn` 不能保护真实账号或数据，只能演示界面跳转，不应用作权限系统。

## 作业和 AI 使用

先遵守教师、课程、学校或比赛的规则。允许使用 AI 时，按实际说明它参与了哪些工作，自己完成了哪些需求、审查和测试。被问到关键代码时，应能解释核心行为和限制。
