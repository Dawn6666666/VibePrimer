同一会话变长后，Agent 可能重新询问已经确认的技术栈，或者把修好的代码改回去。原因可能是关键内容没有进入当前上下文，也可能是长输入中的相互矛盾信息增加了取用难度。

## 长输入不等于稳定记住

一些长上下文研究发现，模型利用长输入中信息的能力会随任务和信息位置变化，部分实验里中间内容更容易被忽略。具体表现因模型、任务和上下文组织方式而异，不存在适用于所有场景的固定“长度悬崖”。相关阅读见 [值得读的](/after/reading/)。

实际使用时，不要把窗口容量当作可靠记忆。需求、排除项和当前进度应保存在文件里，而不是只留在几十轮对话之前。

## 什么时候考虑新会话

| 信号 | 先检查什么 |
| --- | --- |
| 重复询问已确认的信息 | 当前会话是否还能看到需求文件，信息是否前后矛盾 |
| 把已修复的问题改回来 | 是否混入旧代码和失败方案，当前任务是否缺少边界 |
| 多次提出重写整个文件 | 任务是否过大，文件职责是否不清，是否需要新方案 |

同一问题已经纠正多次仍无进展时，可以结束当前尝试。新会话之前先保存结论，不能直接 `/clear` 把唯一记录清掉。

## 收尾后再开新会话

::: steps
1. 把当前需求、已确认事实、失败原因和下一步写入文件。
2. 更新 `TODO.md`，标明完成、未完成和阻塞项。
3. 查看代码改动，提交通过验收的版本；未完成的改动可以先做临时提交或备份。
4. 再清空或新建会话。
:::

项目里常用这些文件：

```text title="常用状态与规则文件"
REQUIREMENT.md   需求与验收标准
TODO.md          任务、进度和下一步
AGENTS.md        支持该约定的 Agent 使用的项目规则
BUGS.md          现象、原因、修复和复测
```

不同工具读取规则文件的方式不同。`AGENTS.md`、`CLAUDE.md` 和 `.cursor/rules` 不是完全通用的同义词，支持对应约定的工具才会按配置加载。首次使用要查工具文档，必要时在当前消息里明确要求读取。

新会话可以这样开始：

```text title="新会话启动提示词"
先读 REQUIREMENT.md、TODO.md 和项目规则文件，不要改代码。
说明项目目标、当前进度、下一步，以及你发现的需求矛盾。
等我确认后再执行。
```

## 提供相关文件，而不是整个仓库

修 bug 时，相关文件可能包括出错函数、调用方、数据定义和测试。只给一个孤立文件也可能信息不足。更稳妥的做法是让 Agent 先读 README 和目录，定位相关文件及其直接依赖，再逐步扩大范围。

长文件可以提供相关段落和准确行号，但行号只用于定位，仍要打开代码核对。不要把密钥、个人信息和无关日志一起贴进去。

## 项目规则文件示例

```markdown title="AGENTS.md 示例"
# 项目说明

## 目标
本地单文件番茄钟，双击 index.html 使用。

## 运行与验证
- 无构建、无依赖。
- 修改后按 REQUIREMENT.md 验收。
- 语法检查使用项目实际可用的命令。

## 当前约束
- 不引入框架和 npm 包。
- 所有运行代码放在 index.html。
- 不改变已有元素 id，除非先说明原因。
- 不读取 .env 或其他真实凭据。

## 当前任务
只处理 TODO.md 中未完成的条目，不顺手重构。
```

规则文件不能替代权限控制和人工审查。它的作用是让支持该约定的工具更容易获得一致的项目背景。

重要约束可以在当前消息里简短重申，例如“本任务仍保持单文件、无依赖”。任务变化后同步更新文件，避免当前消息和磁盘里的规则相互冲突。
