给 Agent 的提示词应当包含完成任务所需的信息。目标、项目背景、限制和验收方法越清楚，它越少依赖猜测。

## 六个常用部分

<PromptBuilder />

:::: field-group

::: field 角色
@type string
@optional
需要哪种专业视角，例如“帮我检查浏览器兼容性的前端审阅人”。角色能引导模型的关注重点，但无法替代具体的约束。
:::

::: field 任务
@type string
@required
当前单次会话要完成的明确目标，一次只派发一个目标。
:::

::: field 上下文
@type string
@required
项目位置、相关文件、已知事实与最近改动。Agent 只能使用已读取或你显式提供的内容。
:::

::: field 约束
@type string[]
@required
硬性条件，包括允许修改的文件、禁用的依赖库、目标运行环境与权限边界。
:::

::: field 验收
@type string[]
@required
具体操作步骤、预期行为结果，以及需要运行的命令或测试。
:::

::: field 不要做
@type string[]
@optional
本任务明确排除的功能和修改范围，防止模型顺手重写其他模块。
:::

::::

并非每条消息都要写满六项。调整一个颜色直接说清文件和行号即可；处理新功能和排查错误则需要把约束与验收写全。

## 三组修改示例

:::: code-tabs

@tab 新功能

**信息不足**

```text
帮我做个报名功能
```

**可以执行和验收**

```text
做一个活动报名演示页，使用单个 index.html，不接后端，不收集真实个人信息。

字段：昵称、人数和提交按钮。
昵称空白时，在按钮下方显示「请填写昵称」。
人数只接受 1–4 的整数，其他值显示「人数应为 1–4」。
校验通过后，在页面内显示报名摘要，不跳转，不写入 localStorage。

只改 index.html，不引入库。完成后给出三条手动验收操作。
```

@tab 修 bug

**信息不足**

```text
点了没反应，帮我修
```

**可以定位**

```text
先分析原因，不要马上改代码。

预期：点「提交」后出现「报名成功」。
实际：点击后页面没有变化。
报错：Uncaught TypeError: Cannot read properties of null (reading 'addEventListener') at form.js:12
相关代码：form.js 第 8–20 行，见下。
已试过：刷新和换浏览器，结果相同。

请区分已确认事实和待验证假设，给一步验证方法，再做最小修复。
```

@tab 调整界面

**难以验收**

```text
界面太丑了，帮我优化一下
```

**要求具体**

```text
只改 style.css，不动 HTML 和 JavaScript。
主内容最大宽度 720px 并居中；标题 28px；正文 15px、行高 1.75。
小于 640px 时，左右内边距 16px，按钮独占一行。
只使用现有颜色变量。改完列出调整过的规则。
```

## 四种常用模板

:::: collapse

### 深入访谈

```text
我要做一个【东西】，给【谁】在【场景】用。
先不要写代码。一次问我一个问题，只问会改变实现方式的问题。
确认后，把最终决定写入 REQUIREMENT.md，用我能理解的语言描述。
```

一次问一个问题适合深入访谈；案例中的“最多十问、一次列完”适合快速补齐需求。两种都可以，完成后都要保存最终决定。

### 先给计划

```text
先不要写代码或改文件。读取 REQUIREMENT.md 和相关文件。
给出文件职责、实施顺序、每步验收和主要风险。
等我确认后，每次只执行一步。
```

### 限制修改范围

```text
这次只做 TODO.md 第 2 步。
优先只改 script.js；如果必须修改其他文件，先说明原因。
不要增加无关功能、重构或依赖。
完成后说明改动、验证结果和未验证项。
```

### 提供验收证据

```text
完成后列出实际运行的命令和关键原始输出。
说明每条验收标准对应哪个操作和结果。
日志先脱敏，不要贴密钥或个人信息。
无法验证的项目明确写「未验证」，不要写成已通过。
```

::::

命令输出能证明命令的退出状态和部分行为，不能证明所有界面细节。界面功能还要附手动操作与观察结果，最好由你自己独立复跑。

## 写多长合适

新任务应一次交代会改变实现的前提。微调可以写得很短。调试消息优先放报错原文、复现步骤和最近改动，不必为了达到某个字数重复背景。

“资深”“神级”“请你一定完美”等称呼不能替代信息。提示词是否有效，主要看任务是否明确、上下文是否足够、约束是否可执行、结果能否验收。

上下文变长后，重要约束可以在当前消息里简短重申，并同步到项目规则文件。下一篇介绍 [上下文管理](/craft/context/)。
