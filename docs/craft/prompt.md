提示词不是咒语，是**工单**。

你给装修师傅的工单上会写：改哪面墙、用什么材料、什么时候完工、不能动什么。你不会写"帮我弄好看点，你懂的"。

AI 也一样。它不缺能力，缺的是你脑子里的那些前提。

## 六格

下面这个东西是可以直接用的。填六个格子，右边实时生成一段完整的提示词：

<PromptBuilder />

六格的顺序不是随便排的：

| 格 | 为什么需要它 |
| --- | --- |
| **角色** | 决定它用谁的视角做取舍。写"有耐心的前端工程师"和写"资深架构师"，出来的东西完全不同 |
| **任务** | 一句话说清做什么。**一个任务只能有一件事** |
| **上下文** | 它看不到你的屏幕、你的文件、你昨天说过的话。你脑中的前提，全要写出来 |
| **约束** | 硬条件：不能装依赖、不能改这个文件、必须几分钟内跑起来 |
| **验收** | 什么算做完。没有这一格，它会自己定义"做完" |
| **不要做** | 排除项。这一格挡掉它 80% 的"顺手" |

大多数人的提示词只有第二格。这就是为什么它总是做出"差不多但不是我要的"东西。

## 三组改前改后

::: code-tabs

@tab 从「做个登录」开始

**改前**

```text
帮我做个登录功能
```

**改后**

```text
做一个登录页。项目是原生 HTML/JS，没有后端，账号密码写死在 users.js 里。

字段：用户名、密码、一个「登录」按钮。
校验：任一为空时按钮下方红字提示；密码错误提示「用户名或密码不对」（不要说是哪个错）。
成功后跳转到 welcome.html，并在 localStorage 里记一个 loggedIn 标记。
welcome.html 打开时如果没有这个标记，跳回登录页。

只改 login.html、login.js、users.js 三个文件。不要引入任何库。
```

第二个版本里，**每一句都是可以被验证的**。第一个版本里，每一句都要靠猜。

@tab 从「修个 bug」开始

**改前**

```text
点了没反应，帮我修
```

**改后**

```text
修一个 bug，先分析原因再动手。

- 预期：点「提交」后出现「报名成功」四个字
- 实际：点了没反应，页面没有变化
- 报错：Uncaught TypeError: Cannot read properties of null (reading 'addEventListener') at form.js:12
- 相关代码：form.js 第 8–20 行（见下）
- 已试过：刷新页面、换浏览器，问题依旧

先告诉我最可能的原因，再给最小修复，最后告诉我怎么自己验证。
```

@tab 从「好看一点」开始

**改前**

```text
界面太丑了，帮我优化一下
```

**改后**

```text
只改 style.css，不动 HTML 和 JS。

1. 主内容宽度最大 720px，水平居中
2. 标题 28px，正文 15px，行高 1.75
3. 按钮圆角 8px，内边距 10px 20px，hover 时背景加深一档
4. 手机上（<640px）左右内边距 16px，按钮占满一行
5. 配色只用现有的两个颜色变量，不要新增颜色

改完告诉我你动了哪几条规则。
```

"好看"无法执行，"宽 720px、字号 15px、圆角 8px"可以。

## 四个随身带的模板

::: collapse

### 一、采访式（想不清楚的时候）

```text
我要做一个【东西】，给【谁】在【场景】用。
先不要写代码。请你扮演需求分析师，一次问我一个问题，
直到你能写出一份完整的需求说明。
最后把需求写成 SPEC.md，用我能看懂的大白话，含糊的地方给我选项而不是替我决定。
```

### 二、计划式（准备动手的时候）

```text
先不要写任何代码，也不要改文件。
读一下项目，然后给我：
1. 需要哪些文件，每个文件一句话说清职责
2. 实现顺序，每一步做完我怎么验证
3. 最可能出问题的地方
等我回复「同意」你再动手，并且每次只做一步。
```

### 三、短绳式（动手的时候）

```text
这次只做第 2 步。只允许改 script.js。
不要顺手优化别的，不要重构，不要引入依赖。
做完告诉我：改了哪些行、怎么验证、有什么副作用。
```

### 四、证据式（验收的时候）

```text
完成之后不要只说「已完成」，给我证据：
1. 你运行了哪些命令，把完整输出贴出来
2. 每条输出里哪一行能证明功能是好的
3. 教我一个 30 秒内我自己能做的验证方法
如果某一步你没法验证，直接说「没法验证」，不要假装验证过。
```

:::

第 4 条值得单独说。**AI 的口头保证不算验收。** 它说"完美解决了"的时候，可能只是它觉得写得不错。你要的是：命令的真实输出、页面的真实行为、你自己点过一遍。

## 长度：什么时候写长，什么时候写短

| 场景 | 长度 | 理由 |
| --- | --- | --- |
| 新任务的第一句 | 150–300 字 | 把前提一次性交代清楚，省掉后面十轮纠偏 |
| 微调（改一个值、换个颜色） | 一行 | 说多了它反而会多想 |
| 修 bug | 100 字 + 报错原文 | 结构固定，信息越全越好 |
| 追问 | 越短越好 | "第二点用方案 B，只改那个函数" |

一条经验：**第一句越短，后面越啰嗦。** 你在开头省的字，会在后面用三倍的对话补回来。

## 四个反模式

::: flex between gap="20"

<Card title="别堆形容词" icon="carbon:close-outline">

"现代、简洁、高级、流畅、友好"——这些词对它没有信息量，只对你有。

换成数字和具体行为。

</Card>

<Card title="别一条消息三个任务" icon="carbon:close-outline">

"做完 A 再做 B 顺便把 C 也改了" —— 它会把三件事混在一起，出错时你分不清是谁引起的。

一次一件，做完再说下一件。

</Card>

<Card title="别指望它记得" icon="carbon:close-outline">

十轮之前你说过"不要用框架"，它可能已经不记得了（[上下文腐烂](/craft/context/)是真的）。

重要约束，放在**当前这条消息**里重复一次。

</Card>

<Card title="别用「你懂的」" icon="carbon:close-outline">

它不懂。它只会猜，而猜的成本由你承担。

把"你知道我想要什么"换成一句明确的验收标准。

</Card>

:::

## 提示词不是越"专业"越好

网上那些"神级提示词""咒语大全"，多数是给通用对话模型调语气的。写代码这件事上，有效的东西非常朴素：

- 说清楚要什么
- 说清楚不要什么
- 说清楚怎么算做完
- 一次只做一件

你不用背任何模板。你只要在按下回车之前，检查一遍：**这四句话，我说了吗？**
