你打开 Agent，第一句话是：

> 帮我做一个番茄钟

这句话里有什么？有一个名词，和一个动词。没有别的东西。

它够 AI 开工了——它会给你一个番茄钟。但它不会给你**你的**番茄钟。区别在于：默认时长是 30 分还是 25 分、归零后自不自动休息、数据存不存、手机上好不好看。这些它都会替你决定，而它决定的方式是"最常见的那种"。

现在我们把它问清楚。

## 让它先问你

在 `pomodoro` 文件夹里打开 Agent，输入：

```text
我要做一个番茄钟网页，本地双击就能打开。

先不要写代码。用提问的方式帮我把需求问清楚：
最多问我 10 个问题，一次问完。只问会改变实现方式的问题，不要问配色和字体。
问题按重要性排序。
```

这是你在 [想清楚](/loop/think/) 里学到的那一招。下面是真实的往来——你可以拿它对照自己。

::: chat title="需求访谈"

{.}

我要做一个番茄钟网页，本地双击就能打开。先别写代码，问我 10 个问题，按重要性排序，只问会改变实现方式的。

{Claude}

十个问题：

1. 时长是固定 25 分钟，还是允许改？改了要不要记住？
2. 「完成一个番茄」算的是什么——倒计时归零？还是中途重置不算？
3. 归零之后：自动开始休息倒计时，还是停下等用户？
4. 关掉浏览器时如果正在计时，重新打开应该继续、暂停，还是回到 25:00？
5. 今日完成数存在哪里？只存今天，还是存历史？
6. 有没有声音提醒？如果没有，归零时你希望出现什么？
7. 手机也要能用吗？如果只用电脑，我就只做桌面布局。
8. 需要「暂停」这个状态吗？还是只有开始和重置？
9. 时间显示用 `25:00` 起还是 `24:59` 起？
10. 一个 `index.html` 还是拆成三个文件？

{.}

1. 固定 25，不改，避免多一个设置界面。
2. 归零才算。重置不算。
3. 停下等用户，不自动休息。第一版不做休息倒计时。
4. 继续。关浏览器是常事，回来接着走。
5. 只存"今天完成了几个"，用日期判断，跨天清零。
6. 没有声音，浏览器会拦。归零时改页面标题。
7. 手机也要能看，但不用为手机单独优化，能居中不溢出就行。
8. 要暂停。暂停后回来接着走。
9. `25:00` 起。归零显示 `00:00`。
10. 一个文件。我要能双击直接打开。

:::

十个问题回答完，需求卡就填满了。注意第 4 条和第 6 条——**那是你在被问之前根本没想到的**。没人问，你就会在写完代码之后才发现"刷新就归零"这件蠢事。

## 需求卡

把它写进 `REQUIREMENT.md`，放在项目里。这不只是给 AI 看的，是给你两天后的自己看的。

```markdown
# 番茄钟 · 需求卡

## 谁用
我自己。宿舍笔记本，Windows，Chrome。

## 什么时候用
每天晚上自习前的 25 分钟。一天用 2–4 次。

## 输入
点两个按钮：开始/暂停、重置。没有文字输入，没有文件。

## 输出
屏幕上：一个 25:00 的倒计时数字、两个按钮、一行「今日完成 N 个」。
浏览器标题栏跟着显示剩余时间。

## 约束
- 单个 index.html 文件，双击就能打开，不装任何依赖
- 不联网，所有数据存在浏览器本地
- 只做桌面布局，手机能居中显示即可
- 一小时内做完

## 不做什么
- 不做登录、账号、云同步
- 不做自定义时长、不做设置页
- 不做休息倒计时（下一版再说）
- 不做任务清单、不做统计图表
- 不做声音、不做通知
- 不用任何框架、不用 npm
```

## 验收标准

六条。每一条都能当场试出来对错。

| # | 标准 | 怎么试 |
| --- | --- | --- |
| 1 | 打开页面显示 `25:00`，标题也显示 25:00 | 双击文件，看 |
| 2 | 点开始，数字每秒减 1；点暂停，数字停住 | 数五秒 |
| 3 | 暂停后点继续，从暂停处接着走，不回到 25:00 | 暂停 3 秒再继续 |
| 4 | 归零时显示 `00:00`，标题变成「休息一下」，「今日」+1 | 把 TOTAL 临时改成 5 秒试 |
| 5 | 刷新页面，「今日完成 N 个」不丢 | 完成一个，刷新 |
| 6 | 重复点开始，不会出现速度翻倍 | 连点五次开始 |

第 4 条那个技巧——**临时把常量改小**——是通用的。你不可能真的等 25 分钟来测归零，把 `25 * 60` 改成 `5`，测完改回来。所有涉及长周期的功能都这么测。

第 6 条现在看起来奇怪。它是这一章的伏笔：真实的第一版，就死在这条上。见 [三个 bug](/case-timer/bug/)。

## 三个决策，和为什么

需求卡里最值钱的不是功能列表，是**那几个"为什么这样选"**。

::: field-group

::: field 为什么不用框架
@type 架构选择

React / Vue 会让"状态变化 → 界面更新"这件事更省心，但代价是：你需要 `npm install`、需要构建、需要 `index.html` 里塞一个 `<script type="module">`。而"双击就能打开"是第 0 条约束。

**约束优先于技术偏好。** 这一条会一直写在你的需求卡里。
:::

::: field 为什么状态存 localStorage
@type 数据存储

"刷新后今日完成数不丢"是验收标准。而单文件、不联网的前提下，`localStorage` 是唯一不需要后端的存储。

代价：它只能存字符串。存对象要 `JSON.stringify`，读出来要 `JSON.parse`，还得处理"第一次打开，什么都没存"的情况。这个代价在第 5 个 bug 里真的咬了你一口。
:::

::: field 为什么用时间戳算剩余
@type 实现方式

最直觉的写法是「每过一秒，剩余秒数 -1」。问题是浏览器在后台标签页会**节流定时器**——你切去背单词，回来发现倒计时少走了 30 秒。

改法：开始时记下结束时间戳，每次 tick 用 `结束时间 - 现在` 算剩余。定时器被节流，只是刷新频率变低，算出来的数字仍然准。

这个决策写在需求卡里，AI 一开始就会用对的写法。**需求卡不只是"要什么"，也包括"别踩哪个坑"。**
:::

:::
