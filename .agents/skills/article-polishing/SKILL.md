# 文章润色与去人机味指南 (Article Polishing)

大模型在撰写或改写中文内容时，极易陷入一系列刻板模式：堆砌行业黑话、过度情绪垫词、滥用宏大比喻、无依据拔高立意，以及使用“不是 X 而是 Y”等固定句式。

本技能沉淀了一套系统的文本去人机化（De-robotizing）原则与操作流程，帮助将文本重构为平实、专业、克制且富有信息密度的真人表达。

---

## 核心原则

1. **真实对话基准**：以真人工程师在日常协作、Code Review 或技术交流中会直接说的话为基线。
2. **事实大于修辞**：讲清“对象、动作、原因与结果”。若一个比喻或修辞没有降低读者的理解成本，一律删掉。
3. **拒绝情绪垫词与廉价捧场**：不使用机械的共情词汇（如“稳稳托住”），不使用模式化的恭维套话（如“抓住了本质”）。
4. **语气克制与平等**：不居高临下，不搞说教，不使用客服式的机械结尾。

---

## 常见 AI 人机腔调与改写对照

### 1. 稳稳接住（拒绝假性共情与过度情绪代入）

* **为什么像 AI**：把普通技术回应换成了现实中极少出现的情感抚慰词，连起来生硬造作。
* **典型表现**：
  - “这一次，我会稳稳地接住你的每一份情绪。”
  - “你的疲惫，我先替你轻轻托住。”
  - “别担心，我会陪你把这一段逻辑慢慢走完。”
* **改写方式**：直接陈述原本想表达的内容。普通回应说“我明白”、“我来看看”、“接下来处理这个问题”即可。

### 2. 单字动作（拒绝生硬串联的单字动词）

* **为什么像 AI**：频繁将“提、收、落、顺、接、铺、拢”等单字强行配给问题、逻辑、情绪和结论，密集堆叠。
* **典型表现**：
  - “这个点先接一下，再往下铺。”
  - “前面铺开，后面拢住，最后往人身上落。”
  - “把力量提一层，把情绪收一下。”
* **改写方式**：删掉无实际动作支撑的单字动词。若删去后原意无损，则直接陈述完整短语或结论。

### 3. 滥用双引号（拒绝普通词外加引号）

* **为什么像 AI**：模型喜欢给普通名词（如真实、用户、价值、看见、连接、骨架）加上双引号，刻意营造高深或反讽的错觉。
* **典型表现**：
  - “让‘价值’真正被‘看见’。”
  - “把‘人’重新放回‘体验’中心。”
  - “这不是‘功能’，而是一种‘连接’。”
* **改写方式**：删掉没有作用的双引号。仅在引用原文、代码符号、专有名词或确实需要表反讽时保留。

### 4. 夸张比喻（拒绝宏大比喻泛滥）

* **为什么像 AI**：普通功能被写成灯塔、桥梁、钥匙、翅膀、引擎、坚固地基、第一道防线，语意宏大而内容空洞。
* **典型表现**：
  - “成为穿越不确定性的灯塔。”
  - “为开发团队插上高效的翅膀。”
  - “打下坚不可摧的地基，锁死第一道防线。”
* **改写方式**：直接交代真实对象、具体动作和实际收益（如“为后续扩展保留清晰接口”、“减少手动配置步骤”）。

### 5. 提升立意（拒绝无依据的价值升华与宏大叙事）

* **为什么像 AI**：一个小工具或基础配置，被拔高到生活秩序、时代变革或人性哲思层面，结论远大于事实。
* **典型表现**：
  - “一个待办清单，承载的是对生活秩序的重新想象。”
  - “这不仅是一次代码重构，更是对未来开发范式的温柔回应。”
  - “当技术退到身后，人终于可以重新成为时间的主人。”
* **改写方式**：论断必须有材料和证据支撑。技术教程或功能介绍应停留在解决的实际问题上，不强行升华。

### 6. 黑话堆砌（拒绝职场黑话与夸大词汇）

* **为什么像 AI**：短时间内密集串入“砍一刀、压实、收口、闭环、落盘、锁死、打下基线、法理裁判、签合同”。
* **典型表现**：
  - “需求卡落盘后，锁死这份共识。”
  - “先把逻辑压实，再把表达收口，打下确定基线。”
  - “需求是唯一的法理裁判，进仓库就是签合同。”
* **改写方式**：
  - `落盘` → `保存 / 写入 / 生成`
  - `锁死共识` → `确认需求 / 明确约定`
  - `打下基线 / 闭环` → `首次提交 / 完成流程`
  - `法理裁判` → `对照依据 / 验证标准`

### 7. 模式化捧场（拒绝廉价恭维）

* **为什么像 AI**：无论用户提出什么，开口必先给一段“抓住了本质”、“思考很深”、“非常精准”的高强度夸赞。
* **典型表现**：
  - “你这个判断非常精准！”
  - “你已经抓住最本质的那一层了。”
  - “你观察得很敏锐，这是一个非常高级的思考。”
* **改写方式**：删掉固定捧场套话，直接进入实际技术分析与问题解决。如果确实有出色构思，具体指出好在何处即可。

### 8. “不是 X，而是 Y”（拒绝反转模板滥用）

* **为什么像 AI**：在没有误解的前提下，给普通陈述强套反转对比，读起来像固定的演讲模板。
* **典型表现**：
  - “不是功能，是体验。”
  - “不只是效率，更是可能性。”
  - “核心不是高深的算法，而是严谨的结对纪律。”
* **改写方式**：直接说原本想表达的内容，例如：“通过分步开发与及时测试，确保代码符合预期”。

### 9. “先说结论”等宣誓性套话（拒绝模式化段首铺垫）

* **为什么像 AI**：答案尚未给出，先预告一通“我先直接说结论：可以”、“一句话总结：方向完全正确”。
* **典型表现**：
  - “我先直接说结论：可以，而且非常值得。”
  - “一句话总结：完全可行。”
  - “先给答案，再把底层逻辑拆开讲清楚。”
* **改写方式**：短问题直接给出答案；长篇分析由内容自然组织段落，不提前宣布套路格式。

### 10. 一句话强行拆列点（拒绝列表割裂感）

* **为什么像 AI**：把语义连贯的一两句话强行拆成 3~4 个独立短行列表，使语篇零碎、可读性下降。
* **改写方式**：只有并列关系强、需要逐条检查的场景才用列表。因果推导或陈述性内容保持自然段落。

### 11. 客服式机械收尾（拒绝假性客套）

* **为什么像 AI**：文章或回答末尾固定出现“祝您生活愉快！如有任何问题欢迎随时联系！”或“希望对您有所启发”。
* **改写方式**：交代完关键步骤与注意事项后干净利落地收尾。

## 技术文档与教程特化规范（参考 Shirone-Docs）

编写或润色技术文档、用户手册与实战教程时，应遵循以下工程化标准：

1. **标题客观化**
   - 避免：`## 立即执行根提交（打下确定基线）`
   - 推荐：`## 首次提交：保存需求文档`
   - 避免：`## 锁定计划提交`
   - 推荐：`## 第二次提交：保存实施计划`

2. **Tip / Warning 技术动机说明**
   - 避免带有情绪化说教或契约比喻（如“进仓库就是签合同，防止偷跑”）。
   - 推荐说明技术收益（如“将需求文档作为独立提交保存，便于后续回顾和版本追溯，在修改代码或出现分歧时也有明确的对照依据”）。

3. **操作时序与步骤展示**
   - 如果一个操作由“发送指令 → 工具执行 → 验证结果”组成，优先使用流程步骤容器（如 `::: steps`），而非左右切换的 tabs，保持阅读时的线性时序感。

4. **复盘总结讲求实际度量**
   - 避免虚浮概括（如“教科书般的提交历史”、“错误在萌芽状态就被掐灭”）。
   - 讲清客观事实（如“分工明确：每个 commit 对应一个具体任务”、“易于定位：单个提交范围小，便于对比和回滚”）。

## 润色执行自查清单

在完成任何文档或文章修改后，逐项核对：

- [ ] 是否删除了“稳稳接住 / 轻轻托住”等不自然的情绪词？
- [ ] 是否删除了无意义的单字动作串（“提、收、落、顺、接”）？
- [ ] 是否清除了普通词外无用的一对双引号（“价值”、“体验”、“看见”）？
- [ ] 是否去掉了灯塔、桥梁、钥匙、翅膀、地基、防线等夸大比喻？
- [ ] 是否避免了未经论证的人性、社会或时代宏大升华？
- [ ] 是否将“落盘、闭环、压实、锁死、法理”替换为客观日常技术词？
- [ ] 是否去掉了“抓住了本质”、“非常高级”等固定捧场话？
- [ ] 是否删除了无误解背景下的“不是 X 而是 Y”模板？
- [ ] 段落是否保持自然行文，没有将简单句子强行打碎成多行列表？
- [ ] 结尾是否干净利落，没有客服式机械套话？
