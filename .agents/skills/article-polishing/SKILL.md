# 通用文章润色与去人机味指南

语言模型在撰写中文内容时，极易陷入一系列刻板套路：堆砌互联网与职场黑话、过度情绪垫词、滥用宏大比喻、无依据拔高立意、生硬反转、机械列表以及在中文标题后附带英文括号。

本指南提供了一套通用的文本去人机化心智模型、典型特征对照库、文体规范与操作流程，适用于技术文档、产品说明、教程手册、博客长文及日常技术交流的审查与重构。

---

## 核心心智模型

1. **平等且真诚**：写作者与读者是平等的交流者。不搞居高临下的布道说教，不搞过度低姿态的假性共情，也不使用套路化的机械捧场。
2. **事实大于修辞**：讲清“对象、动作、原因与收益”。如果一个比喻或修辞没有实质性降低读者的理解成本，一律删掉。
3. **信息密度优先**：删除一切不能提供新信息的形容词、副词与清嗓套话。
4. **符合中文阅读习惯**：拒绝英汉直译带来的被动句与名词化赘语，保持主谓宾清晰、动宾自然的汉语语流。
5. **不搞中英双标冗余**：中文已经表达清楚的概念，不随手挂个英文括号重复翻译。

## 常见 AI 人机腔调与改写对照（13 大典型特征）

### 1. 假性共情与情绪垫词

* **特征**：把普通技术交流换成现实中极少出现的情感抚慰词，语气生硬造作。
* **常见表现**：
  - “这一次，我会稳稳地接住你的每一份情绪。”
  - “你的困惑，我先替你轻轻托住。”
  - “别担心，我会陪你把这一段逻辑慢慢走完。”
* **改写原则**：直接陈述实际动作与事实。日常回应直接说“我明白”、“我们来看这一段代码”、“接下来排查该问题”。

### 2. 单字动词密集串联

* **特征**：频繁将“提、收、落、顺、接、铺、拢”等单字强行配给问题、逻辑、架构和结论，密集堆叠以制造虚假的动作感。
* **常见表现**：
  - “这个点先接一下，再往下铺。”
  - “前面铺开，后面拢住，最后往业务上落。”
  - “把逻辑提一层，把表达收一下。”
* **改写原则**：按中文正常习惯使用完整的动宾短语。若删去单字动词后原意无损，坚决删去。

### 3. 普通名词滥加双引号

* **特征**：给通用词（如价值、用户、体验、看见、连接、地基、骨架）加上双引号，刻意营造高深、深意或反讽的错觉。
* **常见表现**：
  - “让‘价值’真正被用户‘看见’。”
  - “把‘人’重新放回‘体验’的中心。”
  - “这不是‘功能’，而是一种‘连接’。”
* **改写原则**：删除无实际语法作用的双引号。仅在引用原文、代码符号、专有名词、特定术语定义或确需表达反讽时使用引号。

### 4. 夸张比喻泛滥

* **特征**：动辄把普通功能或基础结构比作“灯塔、桥梁、钥匙、翅膀、引擎、坚固地基、护城河、第一道防线”，句子看似宏大，实则空洞无物。
* **常见表现**：
  - “成为开发团队穿越复杂业务迷雾的灯塔。”
  - “为系统架构插上弹性的翅膀。”
  - “打下坚不可摧的底层基石，锁死系统第一道防线。”
* **改写原则**：直接交代具体的组件名称、技术动作与实际收益（如“提取共用工具函数，减少重复代码”、“统一错误拦截，避免页面异常崩溃”）。

### 5. 空洞拔高与立意膨胀

* **特征**：普通功能或常规改动，动辄被拔高到生活秩序、时代变革、人生哲思或行业革命的高度，结论远超事实支撑。
* **常见表现**：
  - “一个待办清单，承载的是对生活秩序的重新想象。”
  - “这不仅是一次代码重构，更是对未来人机协作范式的温柔回应。”
  - “当技术退到身后，人终于可以重新成为时间的主人。”
* **改写原则**：结论严格受制于原材料与证据。技术方案讲清稳定性、性能与维护成本；日常工具讲清交互路径与使用便利，不赋予超负荷的宏大叙事。

### 6. 行业黑话与浮夸词汇堆叠

* **特征**：短时间内密集串入互联网黑话、管理套话或带有夸张威慑力的行话。
* **常见表现**：
  - “把需求落盘后，通过机制锁死这份共识。”
  - “先把逻辑压实，再把表达收口，打下确定基线。”
  - “文档是唯一的法理裁判，进仓库就是签合同。”
* **改写对照**：
  - `落盘` → `写入 / 保存 / 生成`
  - `锁死共识` → `明确需求 / 确认约定`
  - `打下基线` → `完成初始提交 / 确立版本基准`
  - `法理裁判` → `对照依据 / 验证标准`
  - `压实 / 收口` → `确认细节 / 整理总结`
  - `砍一刀` → `裁剪冗余 / 精简步骤`
  - `赋能 / 抓手` → `提供支持 / 采用……方式`

### 7. 模式化廉价恭维

* **特征**：无论对方提出什么问题或方案，开头必先给一段“抓住了本质”、“思考非常深”、“非常精准”的高强度夸赞，显得虚假和迎合。
* **常见表现**：
  - “你这个判断非常精准！”
  - “你已经抓住了最本质的那一层。”
  - “这是一个非常深刻且高级的思考。”
* **改写原则**：删去套路化捧场，直接切入核心事实进行分析。若方案确有长处，结合具体的性能指标、边界防御或可维护性给出客观评价。

### 8. 强造反转（“不是 X，而是 Y”）

* **特征**：在读者或受众并未产生误解的前提下，给普通陈述硬套反转对仗模板，语调像演讲排比，缺乏真诚感。
* **常见表现**：
  - “不是功能，是体验。”
  - “不只是效率，更是可能性。”
  - “核心不是高深的算法，而是严谨的纪律。”
* **改写原则**：直接说明原本想陈述的观点。例如：“通过拆分任务和即时验证，确保每一步改动可控”。

### 9. 宣誓性清嗓套话

* **特征**：结论尚未给出，先预告一通“我先直接说结论：可以”、“一句话总结：方向完全正确”、“先给答案，再把底层逻辑拆开讲清楚”。
* **常见表现**：
  - “我先直接说结论：完全可行，而且非常值得。”
  - “一句话总结：核心就在于解耦。”
* **改写原则**：短问题直接回答结果；长篇分析依靠清晰的小标题和段落自然展开，不提前预报套路格式。

### 10. 长句强行碎裂拆列表

* **特征**：把语义连贯、逻辑自然的因果复句，硬生生拆成 3~4 个带加粗词汇的单行列表项，导致阅读节奏支离破碎。
* **改写原则**：因果推导、背景介绍与叙事内容保持自然段落；仅在具备严格并列关系、需要对照核查、或枚举参数与选项时使用列表。

### 11. 客服式机械收尾

* **特征**：文章、教程或对话末尾固定出现“祝您生活愉快！如有任何问题欢迎随时联系！”或“希望本文对您有所启发”。
* **改写原则**：交代完关键步骤、注意事项或预期结果后利落收尾，保持专业平等的交流氛围。

### 12. 翻译腔与冗余被动语态

* **特征**：频繁使用“对……进行了……的操作”、“作为一个……的存在”、“被成功地完成”。
* **常见表现**：
  - “对配置文件进行了加载的操作。” → 改为：“加载了配置文件。”
  - “作为一个轻量级的存在，该模块表现优异。” → 改为：“该模块体积小、性能稳定。”
  - “任务被成功地完成了提交。” → 改为：“已完成任务提交。”
* **改写原则**：使用主动语态和直接动宾搭配，删去无意义的形式动词（“进行”、“实施”、“作为……的存在”）。

### 13. 括号重复备注与随手挂英文（中英双标冗余）

* **特征**：中文标题、短语或概念已经表达清楚，后面却习惯性挂个括号把英文复述一遍（如“技术博客与架构复盘 (Engineering Blogs & Retrospectives)”、“三步润色法 (Three-Pass Editing Workflow)”），不仅冗余还破坏版面质感。
* **常见表现**：
  - “技术文档与实操指南 (Technical Guides & Manuals)”
  - “润色自查清单 (Checklist)”
  - “核心设计要点 (Core Design Points)”
  - “通用文章润色指南 (Article Polishing)”
* **什么时候保留**：
  - 首次出现的行业标准英文缩写，需补充中文全称（如 `CORS（跨源资源共享）`、`AST（抽象语法树）`）。
  - 代码中的具体 API、标识符、配置项或技术指令（如 `rowspan`、`localStorage`）。
* **改写原则**：
  - 删掉多余的英文括号。中文说得清的概念直接写中文，排版干净平实；行业里习惯直接用英文的词（如 Git、Docker），直接写英文，不要中文译名加英文括号反复啰嗦。

| :--- | :--- | :--- |
| **落盘** | 保存、写入、存储、生成 | “将配置落盘” → “保存配置文件” |

## 文体通用写作规范

### 1. 技术文档与实操指南

* **标题客观准确**：使用动宾短语或名词，直奔主题（如“首次提交：保存需求文档”、“配置数据持久化”，而非带有修饰色彩的“打下坚固地基”）。
* **操作时序清晰**：若操作流程由“准备 → 执行 → 验证”构成，优先使用步骤容器，按真实时间顺序展开，避免无意义的左右并列标签页。
* **说明框注重技术动机**：讲清楚“为什么需要这样配置”、“如果不这样做会有什么潜在影响”，避免居高临下的命令式语气。
* **复盘与小结重在经验提炼**：罗列客观收益（如“分工明确、便于定位、方便追溯”），不写“教科书般的提交”、“错误在萌芽时被掐灭”等浮夸修辞。

### 2. 产品文案与版本更新

* **以用户任务为中心**：说明新功能解决了什么实际痛点、省去了哪些冗余步骤，不空谈“颠覆”。
* **用数据与对比说话**：列举客观指标（如包体积减少 30%、首屏渲染耗时降低 150ms），胜过堆砌“极致流畅”、“飞一般的感觉”。

### 3. 技术博客与架构复盘

* **叙事真实平实**：从实际遇到的问题、选型权衡与排查现场切入，写清“为什么选 A 放弃 B”。
* **结论克制有据**：由测试数据和长期维护经验自然得出推论，不生造“大一统理论”，不上升至时代高度。

## 三步润色法

当拿到一段含有较重“AI 味”或“公文腔”的文本时，按以下三步推进：

```
第一步：脱水（除杂） ──> 第二步：理顺（通脉） ──> 第三步：校准（定音）
  - 剥离情绪垫词        - 改写翻译腔与被动句   - 检验标题是否客观
  - 清理黑话与比喻      - 合并被打碎的列表     - 确认提示框有技术动机
  - 剔除空洞拔高与捧场  - 删去冗余英文括号     - 删掉客服式客套结尾
```

1. **第一步·脱水（除杂）**：
   - 快速通读，划掉所有“稳稳”、“灯塔/桥梁”、“抓住了本质”、“不是X而是Y”、“生活秩序”、“时代”等高频人机词。
   - 将“落盘”、“闭环”、“压实”、“锁死”等词换成最朴素的日常词汇。
2. **第二步·理顺（通脉）**：
   - 检查被动句和“进行了……”句式，改为流畅的主动动宾句。
   - 将被强行拆散成多行列表的完整复句恢复为段落。
   - 删掉普通名词周围的双引号，删掉中文标题或概念后附带的多余英文翻译括号。
3. **第三步·校准（定音）**：
   - 核对标题是否客观明确，不带感叹号与文学比喻。
   - 核对结尾是否干净利落，不拖泥带水，不留客服式尾巴。

## 润色自查清单

修改完毕后，快速扫视文本并逐条打钩：

- [ ] 是否去除了所有假性共情（“稳稳接住 / 轻轻托住”）？
- [ ] 是否清除了单字动词密集串联（“提、收、落、顺、接”）？
- [ ] 是否删除了普通名词上附带的双引号（“价值”、“体验”、“看见”）？
- [ ] 是否去掉了灯塔、桥梁、钥匙、翅膀、引擎、地基、防线等夸大比喻？
- [ ] 是否删除了未经事实支撑的人性、社会、时代宏大升华？
- [ ] 是否将互联网与职场黑话（落盘、闭环、压实、锁死、抓手）替换为自然用语？
- [ ] 是否删除了无意义的模式化捧场（“抓住了本质”、“非常精准”、“高级”）？
- [ ] 是否删除了无误解背景下的对仗反转（“不是 X，而是 Y”）？
- [ ] 是否删除了段首的“直接说结论 / 一句话总结”等宣誓套话？
- [ ] 是否将无必要的列表拆分合并为通顺自然的段落？
- [ ] 是否消除了“进行了……操作”等机器翻译腔与冗余被动语态？
- [ ] 是否删除了中文标题与普通概念后面附带的冗余英文括号？
- [ ] 结尾是否利落干净，无客服式机械客套？
